# Remaining realtime gap: finish the ordinary slice, then close the scalar data pipeline

Review of main `427ef91716597a9bd1a03d477103cb7bad98a230` plus the changing ordinary-scalar slice, 22 October 2026. [Source identities](source-lock.json) capture 33 files at 03:43 UTC. This is a mixed review snapshot: Root changed during inspection; the primary subsequently reported source frozen and the consolidated gate running. No new correctness or speed result is claimed here. This reviewer changed only these report artifacts and ran no test, build, benchmark, browser, server or VM.

## Decision

The active ordinary-scalar slice implements the previous recommendation. Do not rediscover it, interrupt its gate or add another helper optimization to it. Its combined World validator, ordered Root rows, scalar VDOM assembly and optional candidate facade need their existing single boundary verdict.

The strongest additional bounded migration supported by this source is **one enclosed compiled-scalar batch from passive capture through owned output construction**. Today the compiler proves a closed update, but Root reconstructs generic numerical arrays and output descriptions between that proof and VDOM preparation. Move those operations behind one runtime entry, preserving existing capture, evaluation, scalar-delta provenance and publication authorities. This is a vertical change across the computation/output boundary, not a new scheduler, host writer, container, identity registry, instruction machine or collection of independent optimization rounds. [The orchestration](orchestration.md) specifies the exact interfaces, file owners and retired blocks.

This is a candidate for a separately selected unit after the current boundary, not a guarantee that it will close the gap. An approximately 80% reduction in update time would be required against the latest declarative comparator. We have no measured allocation or phase budget supporting that magnitude. If the current slice or this candidate remains slower, the result remains a speed failure; more plausible code changes are not evidence of a feasible performance target.

These are distances to a target, not removable work estimates. In particular, subtracting these interval medians does not identify GPU, draw, validation or allocation cost.

This is one fixed-order Native → declarative React → useFrame → imperative episode, 12 warmup / 60 measured frames, one Apple M4/WebGL2 environment. Frames are dependent. The proof verifies output, identity, actual transforms and teardown; it does not make timings causal, estimate population tails, establish presentation latency or cover matched cold/memory/independent-device gates. The actual archived React transform is more instructive than a generic claim about React overhead. `Position` and `Rotation` each use `_c(8)`, read the external clock, retain an offset and activation control, compute three short expressions, and compare those values plus `children` before creating the next group. `App` retains the scene tree. `FrameMarker` uses `_c(2)`. The update calls `flushSync(() => clock.dispatch(...))`. In the pinned R3F reconciler, `commitUpdate` calls `diffProps`, replaces the prop snapshot and applies changed props; it does not bypass declarative reconciliation. See `proof-canvas-v2/transforms/react/react.tsx.js` and `inputs/r3f-source-basis/reconciler.tsx`, especially its `commitUpdate` around lines 650–677.

Native already skips these owner bodies on the measured closed route: the installed proof reports 257 data rows / one batch per frame, zero kernel executions and zero component renders. “Add memoization” therefore does not address the demonstrated gap. The source still performs source/history capture, expression interpretation, immutable output construction, retained target preparation, validation and accepted publication. Their relative time is unknown.

The comparator is equivalent in authored arithmetic, scene/resource ownership, common draw and checked output, but not in every consistency guarantee. React's application clock is a small frozen snapshot plus listeners. It does not implement Native's complete per-root accepted Store cuts, transition-action replay, forks, holds or explicit multi-root publication. R3F useFrame directly mutates refs under its scheduler; it is a separate realtime authoring contract. Imperative has fewer obligations again. Keep all three comparators and label those differences. Do not weaken Native's contract silently, add irrelevant transaction machinery to React, or replace the declarative arm with the slower frame-hook arm to make a speed claim easier.

## Exact additional migration

Introduce one internal batch operation in `closed_store_execution.ts`, using the existing normalized execution association. It receives ordered owner requests, the existing World and Store transaction; derives state sites/projection paths from the associated program; copies caller request data before captures; calls the existing passive World and Store operations; evaluates rows using one bounded local numeric scratch array; and produces final owned scalar regions once. Root consumes the resulting regions and retained input captures directly.

Keep the current recursive finite evaluator. A private helper can evaluate the scratch array without calling the public `closedDataArray` wrapper because the helper's only batch caller allocated and fully filled that array inside the operation. The existing exported evaluator continues validating arbitrary inputs. No caller-supplied boolean, `readonly` annotation, frozen Proxy, program ID or externally supplied function becomes a trust grant.

Move the existing scalar-region ownership authority out of VDOM into the existing execution module, or a single primary-approved internal extraction if needed to avoid a runtime import cycle. Preserve the public normalizing constructor. The new batch's private constructor uses only its normalized program and primitive results and adds regions to that **same** ownership authority. VDOM consumes those regions using its current preparation/journal path. Do not install a second accepted history or a second mutable source/target registry. Type-only imports can keep `StorePropDelta` shape shared without a runtime cycle.

The operation is passive computation, not publication permission. Source/owner/code/reader/hold/target/writer freshness is still rechecked at existing boundaries. If capture succeeded but later evaluation declines, Root must discard that transaction through the existing candidate decline route; do not retry conservative reads inside the partially populated transaction. Per-reader observations remain independent even when one Store/path capture serves many owners. Original row/prop/write order remains unchanged.

This retires the successful route's per-owner numeric-array allocation, map-to-array append, public array descriptor-copy, second output-pair normalization/copy, and redundant dynamic construction of immutable input/output shape facts already known by the associated program. It does not retire required Store histories, live validation, accepted Root elements, VDOM targets, journals or host writes. An implementation that merely wraps the old calls and leaves all of those named copies in place has not delivered this unit.

## Compiler leverage and the rejected alternatives

The compiler's useful leverage here is **proof of an entire update's data boundary and its input/sink recipe**, not a cosmetic memo hint. Existing schema 7 plus the owned-data association already proves the finite eligibility needed for this migration. Adding another emitted `inputArity` or `propNames` table would duplicate derivable immutable facts; derive them once in the existing normalized association instead. The compiler owner verifies actual emitted metadata and negative controls. No grammar expansion or new schema is needed for this selected unit.

Generated straight-line arithmetic can be faster than recursive evaluation, but reinstating the old `executeRange` callback is not a free solution. A user can supply a function with matching IDs; it can reenter, mutate or throw. The runtime then needs the callback boundary and fresh audits that owned data intentionally removed. A stringified function, function identity brand or compiler-looking name does not prove purity. A new trusted-build-only API would change the extension/security/observable-callback contract and needs an explicit product decision. This plan does not smuggle it in.

A normalized data DAG could recover shared-subexpression work without executing supplied code. The existing Rust `numeric_expression_dag.rs` already preserves expression structure and floating-point grouping for emitted kernels. However, serializing a new instruction graph and interpreting it would introduce another ABI, cold normalization and indexed execution cost. It would also leave capture, history, target preparation and writes intact. The frame expressions are short and share limited expensive work; no evidence says arithmetic consumes the missing 2.75 ms. Therefore **do not implement a new DAG interpreter, cross-owner expression cache, runtime code generation or arithmetic-only rescue in this unit**. Keep this tradeoff explicit rather than claiming that a compiler code emitter is automatically the missing performance architecture.

Similarly, lazy accepted-output materialization could reduce copies but crosses every cache/snapshot/generic fallback consumer. That is a separate accepted-view representation migration, not a harmless deletion of Root mirrors. It is not selected without a complete consumer/invalidation map. Direct mounted writer caching is also deferred: the Three host already caches property resolvers, and cached endpoints require mutable target/lifetime/reset semantics. A second writer registry is not justified by this evidence.

## Realtime contract and limits

The retained scalar path already uses scoped deltas, not mandatory whole-tree replacement. One shared Store does not force every DOM root into a canvas frame. Independent DOM work may run at a separate cadence; explicit DOM/Three coherence still participates in one publication group. Do not pay cross-host coherence without declared intent, and do not remove it from a declared group.

For a single canvas root, old accepted reads while writers run, exact captured acknowledgement, newer pending actions, resource lifetime and partial-host-failure quarantine still apply. Those meanings are required; generic input/output adapter copies between trusted runtime producers are avoidable. This distinction is the defensible answer to “are transactions making the frame slow?” We have evidence of avoidable machinery, not a measured price for each semantic guarantee.

The unchanged trace has 769 changing scalar outputs. Every required mutation remains; Three property dispatch and renderer/readback costs remain. The imperative 0.10/0.20 ms interval is a useful reference, not a measured same-semantics lower bound for Native. If those necessary costs exceed the target, no pass fusion can establish parity. Their bound remains unknown.

Close the active slice first. If selected, run the proposed migration as one reviewed integrated unit with one consolidated correctness gate, fresh installed proof and one bounded unchanged four-arm comparison. No per-helper timings, new recording prerequisite, favorable repeats, VM or worker detour. If it still loses, report that the speed gap remains unclosed; do not turn this report into an indefinite chain of speculative replacements. Full HMR, structural/reveal coverage, lifecycle/cold/memory, independent-device and human-maintenance obligations remain. Zero human participants do not establish a maintenance advantage.

## Additional phase contraction: canonical objects need not pay virtual calls

A fresh enclosed phase operation can audit an exact canonical World/Store receiver and its relevant API shape once per distinct instance, then validate all captured inputs privately. Supporting overridden public methods does not inherently require default canonical objects to execute the same virtual getter twice per cell. This is a sound additional source candidate, not measured savings.

Its result must distinguish `canonical-current`, `canonical-stale` and `public-required`. A noncanonical receiver uses the original public validation loop in its original order. A canonical stale input rejects; it does not retry through public hooks. A private brand check precedes inspection; only exact known ordinary prototypes and own descriptors may be audited. Never walk an uncertain prototype chain or invoke a getter to decide that it is safe. Captured lane/accessor uncertainty remains outside this capability. No permit escapes; class/instance audits expire at the end of the synchronous operation and repeat after every public or host callback boundary.

The important limitation is Root's current validation order. `current(false)` interleaves code/props/reader checks with each owner's public World checks. World canonicality alone cannot justify keeping an audit across an intervening props Proxy, unselected-reader inspection or resource callback. The batch is eligible only when the **entire replaced interval** has owned rows/props, privately registered component metadata, selected canonical Stores and no resource/unselected-receipt callback. Otherwise retain the exact original loop. Do not reorder callbacks to manufacture eligibility. A frozen arbitrary object is not owned provenance. The integration must prove ownership from existing runtime construction, or decline the optimization.

This belongs in the same next vertical unit if that complete passive interval can be established from existing authority. It must not become an independent experiment or a persistent canonical cache. The current ordinary validator also has a finite boxed/zero-lane boundary: do not apply it indiscriminately to public pure-local or lane-backed retained candidates. The primary reported that a consolidated attempt caught precisely such over-broad application; the correction and gate disposition belong to the active unit's record, not this report's performance evidence.

## Larger compiler capability: precise future path, explicitly not completed here

An enclosed runtime evaluator is not the final fulfillment of the compiler-first execution goal. If the next unit still leaves computation material enough to justify a larger capability, the source-backed compiler direction is **prelower the existing numeric expression DAG once**, not restore untrusted executable callbacks:

1. Reuse the finite operators, structural keys, literal bit identity and grouping rules in `numeric_expression_dag.rs`. Refactor its common numeric graph construction so the existing generated-code backend and a data backend consume the same semantic nodes. Do not add a second grammar with different arithmetic rules.
2. Extend the existing owned execution descriptor with a versioned data DAG: bounded input arity; topological numeric nodes; ordered sink-to-node indices; program/revision association. Preserve literal signed zero, operator order, finite input/output policy and the existing treatment of intermediate overflow/NaN. No reassociation, speculative short-circuit execution or broader supported syntax.
3. Normalize and verify this data once at component registration, including exact agreement with the normalized host expressions and input order. Store it in the existing execution association. Replace recursive expression evaluation on this selected route with traversal of those normalized nodes in the **existing** closed evaluator. Keep legacy data programs and generic paths for compatibility. This is an explicit ABI/evaluator extension with cold and memory costs, not a second mutable identity/publication model.
4. Reuse candidate-local scalar scratch; compute each DAG node once per owner. Cross-owner hoisting is excluded initially: equal expressions with different local cells are not equal inputs, and retained/forked Store cuts differ. Any later same-cut Store-only hoisting must use actual snapshot/path identity inside the operation, not a cross-frame value cache.

This recovers compile-time CSE and avoids repeated AST-tree interpretation; it does **not** recover JavaScript arithmetic inlining. True emitted-JS inlining plus arbitrary public descriptor acceptance cannot be obtained merely by attaching a brand. A trusted closed-build contract would be a distinct product capability. No claim that either data-DAG lowering or generated JS alone closes the measured gap is supported. This larger step is specified for an explicit later selection, not silently attached to the active slice or used to prolong its boundary.
