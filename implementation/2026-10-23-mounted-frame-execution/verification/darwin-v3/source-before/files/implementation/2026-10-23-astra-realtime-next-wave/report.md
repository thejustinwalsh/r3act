# Next realtime wave: execute mounted regions without rebuilding their descriptions

**Select one integrated contraction of the existing mounted Store execution path. Make its retained plan the input to capture, evaluation, VDOM application and reader publication; remove the per-frame descriptions that currently connect those stages.** Keep the current compiler kernels, immutable output pages, retained VDOM, live checks and publication state machine. This is a concrete source-supported implementation direction, not a prediction that it will reach React's measured 0.60 ms.

The answer to “are we recreating instances per render?” is **not the mounted component owners, Three objects, meshes, geometries or materials on this stable compiled route**. Eligible component bodies do not rerun. We recreate selections, row objects, input-membership maps, region descriptions, target records, scalar successor nodes and candidate bookkeeping around those mounted instances. Some new state is essential: captured values, exact action/version cutoffs, private pending results and immutable accepted observations must distinguish successive frames. Mount-owned execution descriptions need not be regenerated with that state. React also creates transient render/prop objects; mount lifetime does not mean allocation-free renders.

## Why React's small retained update can be fast

The pinned React19.3/reconciler0.34/R3F10 alpha path does exactly the small work described by the human. Its custom clock dispatches 257 listeners; external-store notifications schedule SyncLane work, one flushSync performs one root render/commit, and unchanged children retain their instances. Position/Rotation execute three scalars and produce one changed motion element each; FrameMarker produces one more. R3F commits 257 hosts and makes 769 scalar assignments, with no per-frame scene/resource reconstruction.

This is stronger than a source conjecture: the [measurement audit](../2026-10-22-react-measurement-audit/results.md) observed all257 subscriptions,257 leaf renders,257 host updates,769 distinct writes and771 snapshot reads inside the original update interval, with drawing afterward. App executes zero times per frame. Compiler-off controls also achieved a submillisecond median; `_c(8)` caching is real, but not a necessary explanation for the fast result. The [actual transform](../2026-10-22-native-frame-publication/proof-canvas-v3/transforms/react/react.tsx.js#L30), [reconciler subscription](../2026-10-22-native-frame-publication/proof-canvas-v3/inputs/installed-store/react-reconciler@0.34.0_react@19.3.0/node_modules/react-reconciler/cjs/react-reconciler.production.js#L3110), and [R3F commitUpdate](../2026-10-22-native-frame-publication/source-basis/r3f-v10/reconciler.tsx#L641) match that account.

Both changing routes are linear in reached owners and writes on this fixture. React is not using a hidden cross-owner arithmetic kernel, and Native's no-body-rerender property does not imply less total work. Native adds more general input/history/publication protections and repeatedly translates their representation. Some protections are an intentional stronger contract than the small clock; their cost cannot be declared removable simply because React is faster. The opportunity is to execute those protections and compiled outputs through fewer representations. No source reading establishes the engine/JIT or millisecond cause of the 4× difference.

## What is right, what is overbuilt, what remains available

**Right:** required Rust/OXC specialization; stable owner/site identity; retained child/resource ownership; real batched shared-input arithmetic; immutable accepted pages; canonical World/Store history; existing immediate/grouped lifecycle; mount-cached key geometry with ambiguity handling; conservative generic execution; failure quarantine. Keep these.

**Overbuilt on the warm owned route:** two near-parallel owner eligibility enumerations; Root row→image→region→VDOM target adaptation; per-cut static reader/projection partitioning; direct reader regrouping during publication; scalar-plan successor copy-back; copying already immutable retained child lists in `OwnedScalarElement` at lines90–95. These are source-observed mechanisms, not measured time shares. The live verification those representations carry is not itself overbuilt.

**Available potential:** existing module facts, bound requests, Root shapes and mounted VDOM recipes already contain enough information to form one reusable execution description. Its consumers still behave as if receiving a fresh generic description. Change those consumers and retire the old adapters together. This is a representation migration across the hot path, not another cache in front of it.

The flat last result is consistent with eliminating only one subset of construction while leaving all these other stages and required work. It does **not prove** that grouping was free, that allocation dominates, or that a particular survivor explains the entire result. The only established performance conclusion is that the geometry refactor's integrated update median/p90 did not improve in that episode.

## Selected candidate and explicit exclusions

Extend the existing `MountedClosedStoreExecution` and Root output-shape authority to describe a mounted closed region end to end: owner/program/input descriptors, unique projection/cohort partitions, original output order, layout/page coordinates, retained templates and opaque VDOM binding. Replace the current owned-frame result with one privately authenticated cut that holds that plan, fresh canonical Store/World capture, immutable result pages and candidate-local accepted-base stamps. Root, Store and VDOM consume the same ordinal relation. Current accepted values remain in Root/VDOM/Store; the plan never stores a second mutable accepted history.

Keep full live reader/target scans and all per-write/final validation in this wave. Static plan facts can replace descriptor/name/uniqueness reconstruction only while their real private origin and existing mounted associations validate. Public arrays, image-shaped objects, Proxy wrappers, overrides and unknown callbacks retain their current defensive interpretation. `OwnedScalarBatchPage.owns(page)` alone does not authenticate a surrounding `{page,rowIndex}` object: current `isOwnedScalarImage` reads a structural wrapper. A private cut must own its coordinates, and VDOM must read them through captured canonical accessors.

Retire the owned warm branch's row wrappers, region wrappers, target-description construction and repeated Store cohort Maps, instead of leaving them beside a new privileged fast API. Cold repair builds the same replacement mounted plan; unsupported shapes use the remaining general retained VDOM route. One public `createNativeFrameLoop`, one candidate lifecycle, one accepted-history model. Preserve old accepted pages by references, not an unbounded plan cache, rotating mutable buffers, finalizers or user release calls.

Do not combine this wave with a new host writer capability, adaptive container, arithmetic backend, worker, cross-component CSE framework or general reveal granularity. The immediate one-root granularity already exists. Independent DOM cadence is already legal outside an explicit group; splitting the game's changing output into independently visible commits would change the workload contract. Host specialization may later be useful, but current source does not establish a stable scalar writer authority that can detect every supported replacement/accessor/proxy/reentry case more cheaply. The generic Three resolver also preserves special property/reset/projection semantics. Do not bypass it on the strength of `mayReenter:false` or a scalar declaration.

## Source-predicted reductions and falsifiers

Let A be selected closed owners, D distinct Stores, P distinct Store/path projections and W changed host props. These are design acceptance counts, not observations of implemented next-wave code:

| Current source construction | Replacement obligation on an unchanged supported mounted frame |
| --- | --- |
| Immediate preflight owner classification followed by passive owner classification | One selection/admission enumeration over existing live membership; no second schema/effect/input reconstruction. Required later freshness scans remain. |
| A `PassiveRow` objects, A output-row wrappers from `makeRow`, A Root region wrappers, A VDOM target descriptions | Plan row identities plus one candidate-owned cut; no copies of owner/tag/key/layout/retained-child geometry in four transport object families. Fresh accepted-base references and cell/version data still require storage. |
| `ownedRequests` unwrap/order comparison before exact reuse | Consume existing authenticated mounted composition; rebuild affected composition on actual binding/selection change. No unbounded cache of every selected subset. |
| Static Store set, readerSources uniqueness Map, projection topology Maps, directRows membership Map; publication readersByStore regrouping | One immutable plan partition reused for capture and publication; allocate D fresh captures/snapshots and P fresh projected value vectors as needed; keep reader-specific history validation/publication. |
| A retained-child array copies in `OwnedScalarElement` | Reuse the exact privately owned immutable child array when its mounted recipe validates. Cold/public children still copy defensively. |
| Frozen scalarPlans/successor copy-back arrays | VDOM binding already belongs to the selected mounted region; install/repair through existing mounted acceptance points, not a per-frame parallel list. |

No promise of zero frame allocation, zero O(A) loops, zero reflection or sublinear dense host work. Until coverage mutation is fully represented and independently proven, the live-reader sweep still makes sparse cost depend on total live readers. Report this honestly rather than selling a new output-sensitive bound. Dense remains Θ(A + W + required history/validation), with a smaller intended construction constant. Root cache/output successors, final page rows, reader histories, exact cell cut and accepted journaling remain legitimate costs.

Hard falsifiers are a second mutable owner/version/publication registry, stale code/owner/binding admission, changed conservative callback order, output/history aliasing, suppressed newer work, fork history merging, retained dead owners, unsafe replay after writes, or generic DOM/Studio progress loss. A source change that merely builds the old objects behind new names fails retirement even if its unit tests pass. A completed migration that remains slower closes its speed claim; it does not automatically select another helper campaign.

## What evidence is sufficient now

Current source selects this coherent contraction responsibly as an implementation experiment: named redundant representations exist and can be replaced while preserving the same semantic checkpoints. It does **not** establish that this is the fastest possible architecture or that its removable share reaches75%. No new diagnostic is a prerequisite for implementing it under the human's cadence. [Orchestration](orchestration.md) specifies one integrated release and one balanced performance boundary.

If the completed boundary still misses parity, preserve it and make a product decision. If a subsequent choice between host specialization and residual transaction work is requested, the missing discriminator is **one current-source, bounded update-ancestry CPU/allocation diagnostic** over the accepted same-output workload with uninstrumented controls and explicit overhead/residual, not old profile percentages or another helper benchmark matrix. It may return unresolved. Do not run that diagnostic automatically or repeat it for a preferred answer. Cold/retained-memory, independent-device and human maintenance claims remain separate unfinished obligations.
