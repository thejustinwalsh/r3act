# Architecture reassessment: compiled incremental execution with scoped publication

**Decision status: planning proposal, not an implemented architecture or speed forecast.** Source basis is `46babf10ce4196a32ba496866a592dc36cdb73c2`. The human requested deep planning after the integrated Store slice; this phase changes documentation only. Preserve the complete product scope in the master guide. The source-grounded [realtime review](realtime-review.md) and [DAG review](dag-review.md) inform this synthesis.

## Assessment

r3act is on the right path with mandatory Rust/OXC compilation, JSX and site identities, retained keyed VDOM, dependency-selected updates, batched closed arithmetic, shared state across hosts, exact root-specific accepted history, and resource/task lifetimes. Current source already reuses bound input requests and mounted scalar plans, emits ranged/batch kernels, and delays ordinary prop/VDOM materialization. The missing architecture is not simply “add memoization,” “add a DAG,” or “introduce mounted plans.”

The imbalance is that compiled arithmetic is embedded inside repeated general discovery, schedule/candidate construction, immutable row construction and publication validation. Current public frame advance delegates Store work to the general queue even when one root has a stable numeric region and no async wait. A scene description is retained, but substantial execution machinery is reconstructed around it. The latest slice removes important duplication without changing that overall shape.

The current matched minified-production scene still loses: update median2.50–2.60ms/p90 2.80 versus React0.60/0.70; through draw4.95–5.00/5.30–5.40 versus2.70–2.80/2.90–3.10. Earlier profile shares are not a decomposition of this changed source. No architecture can be promised to recover the approximately76% reduction from the current median to same-run update parity. This plan identifies named work to retire and falsifiable contracts, rather than inventing a removable budget.

## Keep the product, change the default execution shape

Use one semantic model with three distinct lifetimes:

1. **Module:** immutable compiler plan: sites, closed reads/control dependencies, expression programs, dynamic sink lists, structural operations, effect/value policies, task prerequisites and code revision.
2. **Mounted region:** the existing owner incarnations, live source bindings, mounted targets and execution ranges resolved from that plan. Keep these until topology, source binding, code or owning lifetime changes. Structural deltas repair affected regions rather than rediscover every consumer on every clock.
3. **Update cut:** changed source values/versions, reached outputs, private next accepted values and the exact action cutoff. This is the transient work. Reuse temporary scratch only while it remains private; accepted snapshots never alias writable scratch.

Reader attach/detach, source rebinding and structural/code/lifetime changes must revoke the affected mounted plan through the owning Root and existing binding records. Keep the current full live-membership sweep until all such mutation paths have a proven revocation contract; do not infer freshness from an unrelated root version or replace the sweep with an unmaintained index.

These are representations within existing World/Store/Root/VDOM authorities, not another mutable runtime world. Dependency indexes are derived; they do not introduce an independent version clock. Keep ownership trees, data/task DAGs and publication conflicts distinct: they answer different questions and a conflict relation is not necessarily acyclic.

The default flow becomes:

`dispatch → affected mounted regions → captured inputs → compiled evaluation → existing publication core → renderer observation`

A loader-ready result enters the same captured-input/publication path. The ordinary frame should not recreate a deferred queue handle, dependency map, group facade and row schema description merely to execute one already-mounted region. Make `ComponentStateRoot.#createCandidateLifecycle(spec, immediate=true)` the one-member phase/publication authority, following the existing `#tryFlushClosedStores` → `#prepareInternalClosedInputs` route. Adapt the numeric row executor to supply its capture/apply/ack operations to that same core, then retire its separate direct acceptance via `#publishDirectHostMutation` on the migrated route. Do not remove helpers still used by unmigrated generic paths. Preserve semantics; do not create a second direct committer or benchmark a privileged API unavailable to ordinary JSX authors. Pending resources, competing work, opaque callbacks, structural work or explicit groups use the existing deferred coordination when needed. Eligibility declines before effects or writes; failure after writes never falls back into replay.

## Retained VDOM with less per-frame representation work

Retain topology, keys, component identity, generic reconciliation, host handles and inspectable accepted snapshots. Extend existing lazy materialization from individual scalar frames toward batch-owned accepted value storage: static layout belongs to the mounted region; one private dense output page or changed chunks contain a cut's numeric results. Per-owner views reference that accepted version instead of reconstructing descriptors and frame wrappers for every slot on every frame. This is a proposed replacement for `OwnedScalarBatchRows`/per-row adoption on the eligible route, not a claim that current code lacks compact outputs.

Old observed snapshots, forked roots and in-flight candidates pin their own accepted storage. Never rotate two writable buffers underneath retained snapshots. Publish new private storage only after success; keep old accepted storage through host application and failure. Public tree/prop observations must preserve ordinary enumeration, values and immutability at the same accepted version, with cached materialization where appropriate. Keep finite-number/output checks required by the native value contract; fuse them with production of the final values where sound. For each compiled owner, the mounted plan binds layout and row offset to the root's accepted page reference. Capture that reference once for a public snapshot/serialization traversal. Compiled bound-group old-value reads and `#effectiveLastValue` must read that accepted version; application progress stays private until the core swaps acceptance. Generic bound groups keep their existing representation. A published page never mutates. A saved snapshot owns its page reference, so later root/fork acceptance cannot change it. Root/candidate holds release through existing lifetimes; ordinary saved public objects remain valid until garbage-collected, without a manual release API or correctness-critical finalizers. Avoid a permanently retained page-version chain. Page retention, observation cost and reclamation are explicit cold/memory obligations, not free savings.

## Checks belong to the facts they protect

Move immutable ABI/schema/layout validation to compilation, registration or mount. Live source versions, owner/target incarnation, code validity, resource ownership and accepted histories remain live. After user callbacks or waits, validate the facts those boundaries may change. Keep exact acknowledgement so a host setter's newer action survives. All members of an explicit group must still validate before pointer publication; whole-tree/cache replacement keeps whole-root guards until represented as a safe delta. Arbitrary partial host failure keeps old accepted history and quarantines the affected domain.

Host registration should stabilize writer identity and value/resource policy in the existing host authority rather than repeatedly rediscovering a method through public descriptors. However, a stable writer function does **not** prove callback-free execution: Three setters/copy methods and custom objects can call application code. Retain cheap live target guards around writes and final required validation. Custom mutable/Proxy adapters stay on the defensive path unless they implement the stronger owned contract. Both value policy (scalar/copy/borrow/retain) and possible synchronous reentry must be explicit in the adapter contract; copy-valued does not mean callback-free. After host application, the same lifecycle runs final live validation for a one-member cut or every member of an explicit group immediately before accepted-pointer swaps. A stale result after writes is a partial-failure/quarantine outcome, never a generic replay. No public `trusted: true` flag establishes purity.

The native certified path should not promise transparent support for arbitrary mutation of runtime internals or JavaScript intrinsics. Recommend immutable compiler/runtime-owned internals, explicit code/HMR invalidation and a conservative public boundary. This is a proposed eligibility/compatibility contract to document before implementation; it is not permission to remove existing fallback or live checks silently. Diagnostics and exhaustive developer audits may be stripped; semantic branch decisions remain in production.

## Use the alternatives' mechanisms without abandoning VDOM

| Mechanism | Transfer to r3act | Present status / missing leverage |
| --- | --- | --- |
| Solid's targeted reactive consumers and batching | Source→derived computation→sink invalidation; deduplicate shared pure work per compatible cut; prune unchanged results. | Sparse bindings and a standalone synchronous task graph exist; integrate affected-sink execution with mounted native regions without copying the standalone graph's value store into a new authority. |
| Vue's compiler-informed VDOM, patch flags and flattened dynamic blocks | Retain the tree, execute a compiler-listed dynamic subset and repair lists on structure changes. | Closed programs/mounted plans already exist, but live discovery and general candidate construction still surround the hot path. |
| Svelte's compiler specialization | Generate narrow capture/evaluation/application code from known syntax instead of repeatedly interpreting shape. | Ranged/batch kernels and CSE exist. The opportunity is across the execution pipeline, not another arithmetic-only backend. |
| Incremental computation and Xi's summaries/deltas | Reuse unchanged expensive derived outputs, propagate changed summaries, prioritize demanded work. | Only use associative summaries where the algebra is declared. Full-frame canvas work can prefer a dense range over sparse graph traversal. |
| React's effective subscription cut | Keep static ownership out of clock updates and batch affected work into one publication. | Both systems already retain static scene children. React's0.6ms does not require Compiler; the target is eliminating r3act's extra work around comparable outputs. |

These are design lessons, not comparative speed claims. Vue's general description of React traversal must not override the pinned-source evidence that the measured React arm bails out of unaffected subtrees. Primary references: [Solid](https://docs.solidjs.com/advanced-concepts/fine-grained-reactivity), [Solid batching](https://docs.solidjs.com/reference/reactive-utilities/batch), [Vue rendering](https://vuejs.org/guide/extras/rendering-mechanism), [Svelte overview](https://svelte.dev/docs/svelte/overview), [Xi-derived local research](../../related-work.md).

Choose dense ranges when compiler-known fanout changes almost every output; sparse adjacency when few outputs are reached. Keep the existing layouts while integrating the execution contract. Clustered/tiled selection is a later measured physical option, not a mandatory third mechanism to build now. A DAG cannot make N changed host writes sublinear, and workers/Wasm do not remove host or publication work.

## Preserve and strengthen the loader/dependency DAG

One dependency authority can expose different relation kinds: value prerequisites, invalidation/control reads and resource discovery. Loader hard prerequisites form an acyclic subgraph; publication conflicts are a separate, possibly cyclic relation consumed by the existing root queue. Discovered resource reads are candidate-local observations until validated, not newly inferred compiler hard edges. Share existing source/site/task/code identities and captured versions; use ready-frontier scheduling for loaders, compiled topological ranges for pure compute, and the existing publication queue for conflicting/reveal work. Never traverse the entire loader DAG for a clock-only frame.

For `workspace(id)`, start profile, permissions and recommendations together when `id` is known. Start projects only when profile supplies its account ID. Compute a shared navigation model from profile/permissions/projects once for compatible candidate scopes using the same captured input versions and code revision, with an explicitly pure computation. Matching inputs never make an effectful callback shareable or merge distinct fork publication histories. Reveal navigation while recommendations remains pending if the application policy allows. A permissions change invalidates its descendants without refetching unrelated recommendations; a clock tick does neither. Unknown fetch keys and hard prerequisites cannot be wished away. Dynamic branches must record controlling inputs and conservatively rediscover when those inputs change; opaque callbacks never become statically pure by declaration alone.

Retain existing compiler task inference, async ready frontier, completed-output reuse, native resource adapters and transition replacement. Connect compiler-known/discovered inputs to the existing source/reader authority and demand scopes. Current compiler inference is narrow; do not pretend it already discovers all component-tree loaders or arbitrary helper reads. Shared in-flight requests require provider-owned cache keys, code/input identity, owner leases and abort only after the last interested owner leaves. A borrowed thenable is not owned cancellation. Forks can share transport/results while retaining separate accepted versions and reveal policies. Stale results are rejected even if the provider ignores abort; HMR invalidates code-dependent results.

React's reconciler does not automatically infer arbitrary loaders before component execution. But React applications can implement equivalent DAG/preload behavior with router/data libraries: [TanStack Router explicitly loads routes in parallel](https://tanstack.com/router/latest/docs/guide/data-loading). Our own equal-knowledge study reports144.8ms DAG versus143.6ms preloaded React, against364.4ms sequential. The defensible product opportunity is automatic orchestration from supported compiler metadata, shared derived work and consistent cross-host ownership—not an operation React plus libraries cannot express. It remains unproved that this integration beats equally informed React.

## What to retire and what must remain

Retire frame-local reconstruction of stable schedule/target descriptions when mounted plans own that information; per-prop descriptor construction when batch-owned accepted values preserve observation; deferred queue/candidate facades on eligible immediate one-member cuts; repeated immutable shape/prototype proofs inside an owned interval; and superseded private ABI adapters after current compiler/fixtures migrate. Preserve frozen historical artifacts and do not cosmetically rename their imports or manifests.

Keep chronological Store actions, private candidates and per-root accepted history as distinct meanings. Keep generic retained VDOM, exact captured acknowledgement, newer reentry, root-specific forks, final live validation, resource lifetime, host failure quarantine and explicit coherent groups. DOM and canvas may have separate cadence unless grouped. Structural repair, async completion and numeric updates converge on the same publication core rather than independent acceptance mechanisms.

## Finite migration and acceptance

1. **Specify and consolidate the execution contract.** Map existing bound requests, mounted plans, immediate lifecycle and group receipts to module/mount/cut lifetimes. Define owned host/internal boundaries and accepted-value observation. Name the replaced loops/adapters before implementation; no new registry or helper campaign.
2. **One integrated realtime slice.** Wire persistent region execution, batch-owned immutable accepted output and immediate public frame publication together, preserving deferred/generic/group routes. Retire replaced schedule/output/facade machinery on that route. Review source during the slice; do not measure helpers individually or reject the architecture because one isolated piece lacks a timing win.
3. **One integrated loader/derived-work slice.** Connect existing compiler task metadata, live inputs, shared compute and resource demand to the same region/cut/publication authority. Prove independent readiness/reveal, real hard edges, changed-input pruning, completed/in-flight reuse ownership and cross-host/fork lifetimes. This can be designed alongside step2 but must not replace the realtime hot path with generic DAG interpretation.
4. **Qualify each completed product slice.** Consolidated semantic/package/HMR/resource gates, then one bounded unprofiled matched minified-production comparison with balanced order, median+p90 primary and raw p95/max secondary. Use actual authored public APIs and equal React preload knowledge. Report capture→accepted host publication separately from draw/readback, and loader start/settle/critical-path separately from reveal. Do not label a prepaint observer as presentation. Add cold/setup, allocation/retained-memory and one second physical device before broad performance claims; quick OS smoke remains the platform scope.

Falsifiers include changed callback order on the conservative path, lost newer actions/history, stale code or target reuse, mutable old snapshots, missed dynamic/control edges, request leaks, unsafe partial replay, or dependency work proportional to unrelated branches. Success requires same-run realtime parity or better on median+p90 and useful async behavior; passing mechanism tests alone is not a speed win. The current0.6ms observation is a comparator result, not a portable constant or promised outcome. If the integrated slice remains slower, preserve it if it delivers justified semantics, report the residual honestly, and make an explicit next decision instead of automatically adding caches, interpreters or benchmarks.
