# Astra review: what React’s sub-millisecond update measures

**The timer is valid for synchronous React/R3F publication into the Three object graph. No material timer-placement defect was found. React does not need React Compiler to achieve a sub-millisecond update on this particular workload.** The prior 0.70 ms is an observed median in earlier runs, not a universal React constant. In this new episode, unchanged Compiler-on assets measured 0.95 and 0.90 ms. Rendering and pixel readback follow the timer; calling 0.70 ms the complete rendered frame would be wrong.

This review reads the pinned sources, emitted ON/OFF code, collector/instrumenter, all raw event boundaries, and [primary’s independent recomputation](primary-review.json). It executes no product code, test, build, browser or benchmark. The [receipt](evidence/run-v2/receipt.json) binds the single six-context episode; the [source manifest](astra-source-basis.json) binds this review. Product implementation remains frozen.

The important evidence limits come first. Exact event counts belong to the instrumented copy, whose property observers change execution and invalidate its performance comparison. The original and manual copies establish immediate correct values without those observers; pinned synchronous source connects those observations to the same mechanism. Hooks observe specified render, commit, snapshot and write operations, not every scheduler instruction or future task. Thus “no observed required update tail” is supported; “no CPU work of any kind afterward” is not. Per-frame inspection compares outer-object and retained-child identity and checks mesh/resource types. It does not compare every geometry/material reference with `===` each frame; disposal tracks the 512 original resources. That narrower check does not invalidate the timer answer.

**The actual boundary and ordering.** In frozen `consumer/scene.ts:164–166`, `performance.now()` immediately surrounds `arm.update(frame)`. In `consumer/react.tsx:62–65`, that function creates the new frame, dispatches it inside R3F `flushSync`, and checks the published marker before returning. There is no earlier dispatch of that epoch. Mount, subscriptions, local-control proof, resource creation and warmup occur earlier, as expected for a warm-update measurement. Prior setup and JIT warmup are real excluded costs; they are not execution of the next frame’s changed-value publication.

The copied asset inserts observers after the original start timestamp and before the original end timestamp. The 186,424-event raw stream contains the following sequence for **each of 72 updates**, including all 60 measured updates:

| Work inside the original update window | Observed count per update |
| --- | ---: |
| Clock dispatch / new snapshot | 1 / 1 |
| Listener begin / end | 257 / 257 |
| Synchronous root render / root commit | 1 / 1 |
| Motion component renders plus marker render | 256 + 1 |
| R3F commits for the observed motion/marker hosts | 257 |
| Unique scalar writes, with correct previous and next values | 769 |
| `getSnapshot` reads | 771 |
| `App` renders | 0 |

All listener notifications precede the single root render. Snapshot reads divide into 257 notification reads, 257 render reads and 257 commit-phase Store-instance checks. The collector’s summary does not itself assert exactly 771 reads or include those reads in its generic boundary predicate; primary’s independent raw verification does, and this review separately found zero snapshot/read/write/render/commit boundary violations. All 769 old/new scalar transitions complete before `publishEnd`. Renderer entry/exit follows it. For epochs 1–71, observed later events are renderer calls and explicit microtask/task checkpoints. Epoch 72 starts teardown immediately after draw; its checkpoints and two subsequent root-render/root-commit pairs are explicitly labeled teardown. They are not deferred publication of frame 72.

This matches the installed reconciler rather than relying only on a marker. React 19.3/reconciler 0.34 schedules these external-store changes on SyncLane `2`; `flushSyncFromReconciler` flushes synchronous roots in its `finally` block. The synchronous lane does not register the separate nonblocking Store consistency check, but `updateStoreInstance` still checks the snapshot. The commit tail flushes pending effects for `pendingEffectsLanes & 3`, consistent with all three snapshot reads occurring before return. Immediate ordinary/manual inspection verifies the marker and all 768 changing motion values before draw. Required writes are not waiting for RAF, a microtask, or the renderer.

**Why this is a small update despite the visible scene.** The authored dependency boundary is the main mechanism. Only 256 motion leaves and the marker subscribe. `App` owns the static keyed scene and does not subscribe. React marks the changed fibers and ancestor child lanes, batches notification into one root flush, visits the affected paths, and bails out of unaffected subtrees. It does not rerun `App` or recreate its full element tree on clock frames. The retained child elements come from that unchanged parent, so ordinary runtime bailouts also avoid rebuilding their mesh/geometry/material subtrees. Those omissions apply without Compiler.

The surviving component work is simple: hooks, three multiply/add expressions per motion leaf, and one new motion group element because all three outputs change. Local offsets remain unchanged during timed frames. R3F then uses ordinary `commitUpdate → diffProps → applyProps`: it compares a small prop set, retains host objects when type/arguments are unchanged, resolves dashed property paths and assigns the new scalars. This is 769 scalar assignments into an existing graph, not mounting 256 resource subtrees or rendering 256 objects to pixels inside the timer. Euler setters can perform their normal associated bookkeeping; the count is observed scalar assignments, not every internal arithmetic operation.

At this fixed shallow topology, listener, affected-path, component and changed-prop work scale linearly with affected owners/writes. General trees also incur ancestor/path traversal; the trace is not an exact count of every Fiber visit. React still performs reconciliation and host prop diffing. It has no demonstrated secret numeric kernel, cross-instance arithmetic cache, or early execution of the current frame. The small bounded survivor set explains how ordinary JavaScript can do the measured work quickly. It does **not** derive an exact 0.70 ms from instruction counts, prove a particular JIT optimization, or apportion milliseconds among React’s phases. Those remain unmeasured.

**What Compiler contributes here.** The actual ON transform gives each motion component `_c(8)`. It caches the `id`-dependent effect closure/dependency array and guards its JSX using `children` and the three calculated values. Arithmetic runs before that guard; every timed frame changes those values, so the changing JSX is recreated. The marker cache similarly misses on each changing epoch. `App` has real caching, but its body executes zero times during these updates. The authored `[id]` effect dependency already prevents layout-effect reruns without Compiler; Compiler can avoid closure/dependency-array allocation, while also maintaining its memo cache. No stable net timing effect follows from source alone.

The OFF build preserves the authored files, pinned install and baseline build settings while removing the Compiler Babel plugin; its captured output has no `_c` or compiler-runtime import. All six contexts have the same measured value/pixel digest. The relevant uninstrumented RAF results, in execution order, are:

| Context | Compiler | Update median / p95, ms | Through draw/readback median / p95, ms |
| --- | --- | --- | --- |
| 1 | ON | 0.95 / 2.50 | 4.30 / 6.50 |
| 2 | OFF | 0.70 / 1.10 | 3.25 / 5.10 |
| 5 | OFF | 1.10 / 2.00 | 4.80 / 6.50 |
| 6 | ON | 0.90 / 2.20 | 5.15 / 6.80 |

OFF reaching 0.70 ms falsifies Compiler as **necessary** for this result. Two contexts per condition, fixed order, drift and code/JIT interactions do not establish that Compiler is faster, slower, or irrelevant by a stable amount. Original ON assets in this episode have a different distribution from the prior 0.70 ms episode. Preserve both observations. The observed browser timer quantum is approximately 0.10 ms (`0.09999999403953552`); the 0.95 ms median can arise by averaging central 0.9/1.0 samples, not from 0.05-ms measurement precision.

The manual ON control removes automatic RAF scheduling and clocks the original synchronous update in each browser RPC. It reports 0.60/0.90 ms browser update median/p95. An independent Node clock enclosing that RPC **plus immediate 769-value inspection** reports 1.90/4.52 ms. Separate draw/readback reports 2.60/4.70 ms in-browser. This supports a genuinely small synchronous operation without relying on RAF timing or merely trusting the marker. RPC transport, scheduling and inspection remain included in the outer clock; subtracting it from browser time would not yield a phase cost. Manual execution is a different workload, not another paired speed competitor.

**Architectural consequence.** Keep the existing Astra proposal scoped to the identified Native duplicate: repeated canonical Store audits and temporary receipt round trips during notification acknowledgement. The authority remains Store-owned accepted history plus Root-owned membership/generation; exact histories, newer actions, forks and post-callback validation remain required. The proposed passive cohort replaces repeated same-Store shape work only where its callback-free proof holds. This audit supplies no numerical repair budget, p95 prediction or full-gap solution. The prior unsound audit-removal control still failed to reach React’s timing.

The new evidence rules out chasing a missing Compiler trick or fixing the denominator by excluding required React work. Native already retains static bodies/resources and compiles arithmetic, so copying that shared property cannot explain its excess cost. Any future repair must retire specific repeated preparation/validation/publication work while preserving its stronger contracts; this result does not authorize that repair. Its falsifier remains a source-locked, correct completed slice that fails the agreed end-to-end gate, not a reduced helper count. No implementation or additional experiment follows this review. The historical Native parity failure and unresolved phase/JIT, cold/memory, presentation and independent-device evidence remain unchanged.
