# Offline V8 sample reconstruction repair

The first analyzer invocation (`analysis.json`) stopped on a raw `timeDelta` of `-63` and labeled it invalid. The V3 traces and capture receipt remain unchanged. V8 CPU profile deltas are signed: DevTools reconstructs sample timestamps by cumulatively adding them, then orders the timestamps together with their sample IDs. A negative raw delta can therefore describe an out-of-order sample point; it is not by itself a malformed profile.

`analyze-profile-v2.mjs` preserves every raw sample ID and raw delta. Starting at the `Profile` head trace timestamp, it cumulatively adds the signed deltas, then stable-sorts sample points by timestamp and original index. The sample ID remains paired with its original point as payload and is not a tie-break key. It derives nonnegative backward weights as the difference from the preceding point in chronological order. The earliest point has no preceding interval and receives no inferred weight. Ties receive zero weight. No raw delta is clamped, discarded, or rewritten, and no interval after the final sampled point is extrapolated.

Window membership uses the chronological sample-point timestamp for point and update-ancestry counts. Weighted attribution uses the derived backward interval only when that full interval falls inside one User Timing update window; crossing intervals remain boundary-unattributed. The result reports raw negative-delta counts, raw min/median/max, sample reordering and timestamp ties, derived positive cadence, point counts, interval weights, and coverage gaps separately. These weights remain sampling estimates, not exact CPU self time.

The method follows Chrome DevTools' [CPUProfileDataModel.ts](https://raw.githubusercontent.com/ChromeDevTools/devtools-frontend/main/front_end/models/cpu_profile/CPUProfileDataModel.ts), especially its cumulative addition of signed deltas (lines 131–140) and sorting timestamps with matching sample indices (lines 244–260). The source receipt, original analyzer, failed `analysis.json`, raw traces, and browser receipt are treated as frozen inputs. This repair is offline only; it does not alter or repeat the browser capture. The result is written separately to `analysis-v2.json`.
