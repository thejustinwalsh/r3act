Holding that old React denominator fixed, Native needed 2.05 ms (67.2%) less median update time and 1.50 ms (42.9%) less p95 time. Those are historical target distances, not removable phase budgets or a forecast for compact output. No current scalar-frame timing exists. The fixed-order 12-warm/60-measured episode is descriptive, with dependent samples and one environment. Through-draw includes common graph inspection, render, pixel allocation/readback and checksum; it is not presentation. State age starts at update entry, not physical input arrival. Subtracting interval medians does not identify a renderer phase.

The comparison remains useful for the requested product: ordinary declarative state drives 256 retained motion groups and a marker before a common draw, with independent local offsets, identical expressions, pixels, identity and 512 exactly-once resource disposals. Native uses a real Store and `root.flush`; React uses `useSyncExternalStore`, a frozen snapshot/listener clock and R3F `flushSync`. The latter clock does not implement Native's chronological actions, fork-specific history, resource holds or declared multi-root publication. Thus this is equivalent visible interaction and declarative ownership, not identical transaction guarantees. Those extra guarantees are real costs to budget; they do not make the stronger declarative result invalid.

I inspected the pinned package, generated transform, R3F source and installed bundle rather than assuming how React works. Versions are React/React DOM 19.3.0, React Compiler 1.0.0, R3F 10.0.0-alpha.6, reconciler 0.34.0 and Three 0.186.1. The generated `Position`/`Rotation` functions use `_c(8)`, retain activation closures/children, calculate three scalar expressions and create a group element when those props change. They do not skip the changing expressions. `FrameMarker` uses `_c(2)`. R3F `commitUpdate` validates the instance, checks reconstruction, calls `diffProps`, replaces its instance prop snapshot and applies changed props. The delivered `diffProps` skips reserved props, compares with `is.equ` and handles dashed-property dependencies; `applyProps` resolves the Three property, handles typed/copy/event cases and ultimately assigns scalar values. This is a genuine declarative reconciler path, not a hidden layout-effect mutation adapter.

The separate useFrame arm registers update-phase callbacks and a render-phase takeover with the pinned scheduler; manual `advance` invokes ref mutations. Proof verifies no scheduler draw during advance and one common draw per frame. React does not reconcile every frame callback. That arm and the imperative loop have different acceptance obligations; their times are neither a universal R3F result nor a same-contract lower bound for Native. Keep them as separate controls and retain the faster declarative comparator.

Independent DOM cadence is compatible with this design. Coherence is required for an explicitly declared transaction, not merely because a DOM root and canvas root share a Store. No scheduler change or worker is needed to express that distinction.

## Exact validation endpoints, without attributing time

For a successful immediate ordinary owned-Store candidate with no fallback, the source has **six full calls to `#isStorePropDeltaCurrent`**:

1. End of `#prepareStorePropDelta` via `isStorePropDeltaCurrent(token)`.
2. `complete.validate()` → lifecycle `validatePrepared` → scoped program `validate`.
3. `complete.commitAdmitted()` → lifecycle `preHostPrivateCurrent` → scoped program `validatePreparedPrivate`.
4. After publication begins, scoped program `commitAdmitted` → `commit` validates with `allowActivePublication=true` before `#applyCheckedStorePropDelta`.
5. `complete.publish()` → `preparePublication` → lifecycle `validatePostHost` → scoped program `validatePostHost`.
6. After Store publication preparation, lifecycle `finalPrivateCurrent` → scoped program `validatePostHostPrivate`.

These each scan the candidate's bucket members and targets; they do not each rebuild the owner index. Additional `#isStoreTargetReady` calls precede changed image writes, and application ends with the existing target-VNode sweep. Counts differ for retries, generic/mixed candidates or explicit groups. The skipped `ownedStoreOnly` preparation check and checked-application helper mean there is no seventh ordinary full Store check at the composite completion/application seam.

Between 1 and 2, preparation finishes and an enabled profile callback can run; timing leaves it null. Endpoint 2 also participates in public Root/Store/World/code validation, whose public override/fallback paths may call user code. Endpoint 3 is the private sweep after those public checks. Between 3 and 4, host domains are claimed and publication/journal state changes to active; a source-proven immediate subcase may be callback-free, but the required publication-state predicate also changes. Between 4 and 5, arbitrary host writers can dispatch, dispose, replace methods, observe snapshots or throw. Between 5 and 6, remaining public validation and `preparePublicationAfterHost` occur; the final private sweep protects against those callbacks, including grouped peers. These separations are why removing a loop by counting it twice is unsound. The selected follow-up removes **none** of these endpoints or per-write guards.

## Concrete conditional contraction

**First priority is the existing boundary.** If correctness/proof/HMR fail, repair that exact failure and rerun a fresh consolidated gate; preserve earlier receipts. If current compact output achieves all same-run parity checks, do not dispatch another speed patch. Proceed to the existing lifecycle/cold/memory and independent-device obligations. If it still loses, this review offers one bounded follow-up candidate, not an automatic chain of remedies.

The follow-up combines two source-local deletions into one ordinary execution slice:

- **Root: reuse before allocating.** In passive preflight, validate `cache.output.shape.boundInputs` directly against the current program/cache props/live memberships. If exact, retain those same frozen input records and the bound request. Allocate `rowInputs` only for cold or changed input binding. Use the existing candidate-local coverage set as remaining selected readers: populate during selection, delete each exactly covered reader, then require it empty. Keep phase-specific live coverage checks. This removes the temporary per-reader records and the later comparison against their copies. It does not cache validity across callbacks or frames.
- **Producer: capture verified numeric output directly into the final frame.** Normalize the numeric-result-to-prop mapping once under the existing immutable layout/execution facts. The frame module allocates, fills, validates and freezes the final private values array in one capture operation, reading only private kernel scratch on this internal route. The general `OwnedScalarFrame.create` keeps its defensive copy; interpreted/public tuple routes keep compatibility. Remove the verified branch's intermediate `props` array, rather than adding another representation alongside it.

For the frozen scene, source counting predicts removal of 257 temporary Root input records/arrays on bound warm frames, and 257 intermediate scalar arrays containing 770 prop slots (three per motion owner plus the marker's two props). This is a count expectation to prove, not bytes allocated or elapsed savings. One final frame array per owner, existing scratch, reader histories, target records and all live validation remain.

`OwnedScalarLayout.slotAt` currently has no live-source consumer found in `src`; its slot array may be repurposed for the verified result mapping rather than adding another array. The mapping must follow `numericPropIndices`, which **includes numeric literals** and excludes nonnumeric literals. Dynamic-slot numbering alone is not equivalent. No new compiler ABI, generated string compilation or per-row callback is needed.

The outer `closedDataArray(orderedRequests)` still looks avoidable for privately assembled Root requests, but deleting it without an owned batch abstraction would launder caller arrays/getters into passive capture. Adding a builder/token protocol solely for that saving is not selected here. Likewise, repeated lineage capture, cell-cut reconstruction, full reader scans, phase audits and lifecycle closure allocation have source-visible costs but no measured budget. Leave them out of this candidate. This prevents a small clear deletion from becoming another broad mutable execution-plan subsystem.

## Limits and decision

Compiler specialization can remove component execution and generic object construction; it cannot make 769 required host mutations disappear, merge distinct owner histories, omit source/code/writer checks across callbacks, or safely publish current values into previously saved snapshots. React's smaller clock contract and compact component/host path may remain cheaper for tiny all-dirty expressions. That is a plausible explanation, not a measured attribution or impossibility proof.

There is no measured removable budget for either follow-up deletion, no established same-contract host floor, and no basis to predict that they close a 67% historical median deficit. The relevant falsifier is unchanged end-to-end parity after the full candidate is correctly integrated. If the next selected contraction passes its mechanism proof but loses, report that outcome and stop this candidate; do not append another registry, interpreter, validation removal or host specialization. Full product progress can continue without a competitive-speed claim.

Historical Snake lifecycle ratios 0.508/0.513, the qualified dense DOM loss, exhausted Recording A/physical HOLD, equal-preload async parity and zero human maintenance participants retain their own scope. This review neither repeats Recording A nor narrows the finish line. Broader realtime/structural behavior, useful async UX, HMR, cold/retained-memory costs and independent-device qualification remain open. Maintainability here means deleting duplicate representation and keeping one invariant authority; it is not an established human maintenance advantage.
