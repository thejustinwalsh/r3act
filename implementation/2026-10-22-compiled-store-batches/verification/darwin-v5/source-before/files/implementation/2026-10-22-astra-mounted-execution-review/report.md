## Representation decision and complete mutation/consumer map

Use an immutable **successor recipe**, not a mutable mounted-value cache. A recipe references the exact existing owner, program, source-description inputs, accepted cache output, VDOM root, mounted node and accepted VNode. After a successful scalar candidate, the new cache shape receives a successor recipe referring to the new accepted VNode. The old recipe remains valid only for its old candidate/snapshot, and cannot be reused against a newer VNode. Recipe fields are derived guards, not new versions or publication authority. No extra Map/WeakMap of owners/targets/writers is introduced.

## Chosen integrated mechanism

1. **Bind static input descriptions once.** Reuse the existing execution association for program facts. A private-class receipt held by the cache shape owns the normalized owner/key, ordered Store/reader/path and World owner/site descriptions. Existing public-shaped APIs still normalize untrusted records; private instances bypass only descriptor *recopy*. World/Store still capture fresh values, versions, root epoch and lineage and perform canonical audits. Preserve the distinction between untouched `public-required` fallback and discard after staging has begun.
2. **Bind a mounted scalar target after a real owned candidate.** Derive an opaque immutable successor recipe from the existing Store delta record's private `target.next`, frozen props and checked children. Its static fields are prop order, target identity, scoped source identity and accepted shape. The cold path remains current `prepareStorePropDelta`; after successful publication Root retains the successor in its existing shape field. Binding alone makes no writes and advances no accepted state.
3. **Use the recipe on warm Store-only scalar preparation.** Check recipe/root/node/accepted-VNode and current placement/membership/child guards. Consume the already owned output tuples, check prop count/order, then create only the new immutable accepted prop record/VNode and compact candidate target. Retire prior-prop descriptor enumeration, recapture of owned scalar old values, name Set, repeated bucket-owner reconstruction and per-prop `(name,next,previous)` staging tuples. The application loop iterates the existing output tuples and reads `previous` from captured immutable accepted props. It still uses Object.is and the current host writer in original order.
4. **Keep exact live admission.** Current Root cache identity, owner/incarnation, code, read/control/hold state, Store lineage and final private checks remain. VDOM writer identity is rechecked after callbacks and before each changed owned scalar write. Binding is not admission. Existing prepared deltas retain their conflict model; whole-tree/cache replacement guards remain untouched.
5. **Publish once, then reuse the successor.** Root prepares actual authored/expanded immutable RuntimeElements as today. VDOM prepares a new immutable VNode. These have different contracts and prop layouts; forcing one shared props object would leak `key`/children/owner metadata into host props or add a new view layer. Keep the necessary separate final snapshots, but share the one existing immutable scalar output list. Only callback-free successful publication installs the successor recipe. This deliberately retires repeated *interpretation*, not accepted history.

The cold/warm split applies to all existing eligible owned scalar schemas, including retained-child motion and the scalar literal marker, not hard-coded benchmark names/arity. Schema5 cache props need not be frozen: preserve their descriptor/source-identity checks instead of silently strengthening authoring semantics. Unsupported values, arrays/styles/copy props, selectors, mutable/unowned inputs, legacy callbacks, lane cells, generic/subtree/resource/mixed structural routes keep their current behavior.

**Retained costs:** fresh World/Store captures and independent histories; complete reader coverage; per-candidate immutable output; Root authored/expanded records; one VDOM accepted props/VNode per changed target; live validations; host-domain coordination, journal, host writes and exact acknowledgements. Do not claim those disappear. New costs are cold binding, immutable successor records and retained static references. No new traversal family, container, writer registry or version field is selected.

## Comparator and benchmark audit

The actual [React transform:30](../2026-10-22-verified-scalar-execution/proof-canvas-v1/transforms/react/react.tsx.js#L30) uses `_c(8)` in each motion component, retains activation closures/children, computes scalar arithmetic and produces new group JSX when outputs change. `App` caches its static tree ([139](../2026-10-22-verified-scalar-execution/proof-canvas-v1/transforms/react/react.tsx.js#L139)). The declarative arm's frozen snapshot/listener clock is simpler than Native's Store. Nevertheless it executes actual per-frame declarative state reconciliation and owns the same retained Three resources; it is the right primary comparator for the selected product interaction. It does not prove parity for Native's additional fork/group/chronological-log contract. `useFrame` assigns passive input and advances the actual R3F scheduler ([react-frame.tsx:122](../2026-10-22-verified-scalar-execution/consumer/react-frame.tsx#L122)); its ref writes do not publish declarative Store state every frame. Imperative writes are a separate API floor, not an identical-semantics removable-cost bound.

I found **no definite output/timing omission that invalidates the current descriptive update-step comparison**. Keep it unchanged. Its limitations are material:

- [scene.ts:163–190](../2026-10-22-verified-scalar-execution/consumer/scene.ts#L163) measures update through the returned accepted marker. The marker lookup is included in each arm. Full graph validation is outside update timing but **inside** update-through-draw and state-age; draw includes allocation/readPixels/checksum. These are neither pure renderer cost nor physical presentation latency.
- State age here is update start to draw start, not age since external input arrival. Fixed arm order, 12 warm/60 measured, roughly 0.1 ms quantization, one page/environment and dependent frames limit inference. Different native/react setup intervals are not matched cold costs.
- The local control proof resets offsets before measured frames. Hence this workload covers retained local capability and Store-driven mixed expressions; it does not time ongoing simultaneous Store-plus-local actions. Keep that test as an untimed semantic regression; do not change the favorable workload to manufacture a win.
- Baseline timing is unminified for all arms. Minified/rebundled/CSP runs are delivery proofs. A future default-minified performance protocol is separate, not a way to rescue this boundary.

## Decision, falsifiers and remaining obligations

Proceed to the source-reviewed three-packet implementation in [orchestration.md](orchestration.md). The structural delivery gate requires warm reuse to bypass the named descriptor/target preparation while retaining all current outputs and guard phases. A cache that still performs all cold preparation, duplicates mutable accepted values, changes authoring semantics, retains removed resources after cache/candidate release, or skips live checks is a failed implementation.

One unchanged boundary comparison decides observed parity: Native update and through-draw median **and** p95 must each be no greater than the declarative arm in that same run. If not, record FAIL and close this slice as an unproved parity solution. Do not attribute the miss to GC or add a favorable rerun/new cache. The broader product goal remains active, but this report does not establish a further source change guaranteed to recover the rest.

Cold setup, retained bytes, allocation/GC, whole lifecycle, independent device, current workbench HMR delivery, broader structure/reveal and maintenance evidence remain open. Historical narrow wins and qualified dense losses retain their own scope; human participants remain zero. RAF/canvas/Three is the current priority, DOM cadence remains independent unless a coherent group is explicitly requested, and DAG work here means same-thread binding/batching—not workers or I/O overlap. The master plan's complete finish line is unchanged.
