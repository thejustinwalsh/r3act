# Podman disposable Linux verification setup

Basis: r3act main `d6c83e26`; user selected Podman instead of continuing Apple Container's coupled service/storage setup. This unit replaces the unavailable Apple-specific verification transport with a dedicated Podman host launcher. It does not change the product compiler, runtime or host semantics.

## Installation and resources

Homebrew installed Podman 6.1.4 on the system drive, with its download cache under `/Volumes/Depot/Containers/podman/homebrew-cache`. The [saved wrapper](podman-wrapper.sh) routes configuration to `/Users/mini/.config/podman-depot`, VM data to `/Volumes/Depot/Containers/podman/data`, and caches/temp/runtime files to Depot. The dedicated AppleHV machine is `r3act-dev`, rootless, one CPU, 1024 MiB RAM, 20 GiB sparse disk, zero configured swap, Rosetta disabled. No administrator helper or login startup was installed. Depot permissions remain unchanged. [Installation settings](installation.json) and [actual live proof](machine-proof.json) record the exact boundary.

The first 512-MiB boot failed with initramfs unpacking error and kernel panic; [console](boot-512m/console.log) and [configuration](boot-512m/machine-config.json) survive. Retrying that incomplete disk at 1024 MiB omitted the ignition device and failed; its [console](boot-1024m-incomplete/console.log) survives. A fresh 1024-MiB boot completed, but its processes disappeared after the startup tool session ended; the first readiness capture correctly remains NOT_READY. A stale API socket and repeated non-overwriting ignition configuration caused further preserved startup failures. A clean initialization/start in one owned bounded session then produced actual running engine evidence. Session lifetime is an operational constraint, not an application benchmark. 1024 MiB is the lowest successfully booted setting tried, not a proved theoretical minimum.
