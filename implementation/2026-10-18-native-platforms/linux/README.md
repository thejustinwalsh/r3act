# Apple container Linux ARM64 route

Status: Apple container route source prepared, **unexecuted**. Historical Docker/Colima v1 and v2 results are preserved in [Linux delivery results](../../2026-10-18-linux-delivery/results.md). This local route uses Apple container 1.5.0 with `CONTAINER_APP_ROOT=/Volumes/Depot/Containers/apple/data`. Service installation and start are separate user-controlled operations. The scripts never start or stop the shared service, publish ports, prune images or volumes, or touch another container.

`prepare-image.mjs` pulls the official `node:24.18.0-bookworm` ARM64 image and records its resolved OCI digest and Apple CLI/API version. It does not invoke the shared BuildKit builder. The first named, labelled bootstrap container installs Rust 1.97.1, Deno 2.9.7 and pnpm 11.25.0 into the owned workspace volume, verifies the Rustup and Deno release checksums, and records tool versions and download hashes in `toolchain-proof.json`. The bootstrap and every later container phase have deadlines and owned-container cleanup; failure logs stay in the exclusive image/evidence directories. Base image pull is separately bounded at the CLI, although an interrupted remote image transfer may need inspection before retry.

After primary source review, Luna may use these commands with new, absolute output directories:

```sh
node implementation/2026-10-18-native-platforms/linux/prepare-image.mjs --output-dir "$PWD/implementation/2026-10-18-native-platforms/linux/image-v1"
node implementation/2026-10-18-native-platforms/linux/run-linux-arm64.mjs --image-proof "$PWD/implementation/2026-10-18-native-platforms/linux/image-v1/image-proof.json" --evidence-dir "$PWD/implementation/2026-10-18-native-platforms/linux/evidence-v1" --phase bootstrap
node implementation/2026-10-18-native-platforms/linux/run-linux-arm64.mjs --image-proof "$PWD/implementation/2026-10-18-native-platforms/linux/image-v1/image-proof.json" --evidence-dir "$PWD/implementation/2026-10-18-native-platforms/linux/evidence-v1" --phase verify
```

Bootstrap creates one labelled, size-bounded named volume under Depot. Each phase requests one CPU, 256 MiB memory and one Cargo build job for its short-lived labelled container, with a hard deadline; the named volume keeps the same Linux workspace and toolchain across phases. The host receipt records the requested cap, not an observed effective limit. This low-memory setting has not been verified to complete bootstrap, compilation or the benchmark. Increase a specific phase cap only after its preserved failure shows a resource need and primary reviews the new bound. The checkout is mounted read-only. Bootstrap uses `scripts/native_verification_inputs.mjs` to copy the current native runner inputs, Linux phase controls and benchmark source, including required examples, fixtures and design provenance. It excludes host `node_modules`, Cargo `target`, `.cache`, `.git`, old verification directories and generated proof/evidence. `container-source-lock.json` hashes every selected source before and after copying. Later phases execute the copied control script, compare every copied file to that lock, and check the actual host control script and shared staging helper against it. The host launcher hash, source-lock hash and toolchain-proof hash are bound into the owned-volume receipt. The shared native-platform runner creates its own fresh evidence directory, installs with the frozen lock and checks the actual Linux ARM64 target, compiler artifact and installed consumer.

Only after the correctness receipt passes and primary releases the benchmark should Luna run `--phase benchmark-prepare`. It performs the required untimed proof builds in the **same volume**, then copies reviewable evidence to the host while excluding installed `node_modules` except the exact compiler binary and manifest. Primary reviews `benchmark/proof-v1/build-proof.json` and writes the hash-bound `run-authorization.json` into that host proof directory. Luna then runs `--phase benchmark-run`, which copies only those authorization bytes into the volume, checks they bind the unchanged build proof, and executes the single native-first pair. `--phase archive` copies incomplete proof after interruption without rerunning work. `--phase finalize` deletes only the receipt-labelled owned volume after evidence review. Every phase has an exclusive receipt and raw host logs; a failed phase is not silently retried.

This proves a Linux ARM64 native build/consumer case inside a VM on the same Mac if the future gate passes. It is not a separate physical machine, cold-cache timing, runtime latency or hosted CI result. The required untimed proof builds can warm filesystem caches before the one timed pair.

## Docker/Colima alternative

`run-docker-arm64.mjs` uses an already running Linux ARM64 Docker daemon. It does not start, stop, reconfigure or prune the shared daemon and publishes no ports. Its container cap does not lower the daemon VM's own memory allocation; inspect any existing Colima profile before using this route, and do not implicitly restart an old high-memory VM. Colima's current VM does not mount Depot, so this route transfers an explicit source snapshot through `docker cp` into an owned source volume, mounts that volume read-only during each phase, and exports an owned evidence volume back to an exclusive Depot directory after each phase. The workspace/toolchain and these transfer volumes occupy the Docker daemon's storage; Docker provides no per-volume disk quota here. The image proof records the actual daemon identity, root path, resolved official Node 24.18.0 Bookworm repository digest, ARM64 image ID and runtime limitation. A Colima VM on the same Mac is not independent hardware.

After primary source review, Luna may use these commands. The output directories must be new and their names must start with `image-docker-` and `evidence-docker-` so source selection excludes them.

```sh
node implementation/2026-10-18-native-platforms/linux/run-docker-arm64.mjs --phase prepare-image --output-dir "$PWD/implementation/2026-10-18-native-platforms/linux/image-docker-v3"
node implementation/2026-10-18-native-platforms/linux/run-docker-arm64.mjs --phase bootstrap --image-proof "$PWD/implementation/2026-10-18-native-platforms/linux/image-docker-v3/image-proof.json" --evidence-dir "$PWD/implementation/2026-10-18-native-platforms/linux/evidence-docker-v3"
node implementation/2026-10-18-native-platforms/linux/run-docker-arm64.mjs --phase verify --image-proof "$PWD/implementation/2026-10-18-native-platforms/linux/image-docker-v3/image-proof.json" --evidence-dir "$PWD/implementation/2026-10-18-native-platforms/linux/evidence-docker-v3"
```

The Docker route reuses `run-container.mjs` for bootstrap, native verification and benchmark phases. The host snapshot and container bootstrap both use `scripts/native_verification_inputs.mjs`, so their independently hashed manifests select the same current inputs and exclude historical verification and generated proof trees. Existing source-lock files and historical v1/v2 manifests remain intact. The Docker launcher owns three labeled volumes and short-lived labeled containers, requests one CPU, 256 MiB memory and one Cargo build job for work phases, and keeps hard phase deadlines and original failure receipts and logs. Transfer and space-probe containers retain their separate one CPU/128 MiB caps. The host receipt records requested work limits, not observed effective limits. These caps are unverified for compilation; raise a specific phase only after a preserved resource failure and review. `--phase archive` exports incomplete evidence without rerunning work. Benchmark preparation, reviewed authorization, one bounded benchmark run and finalization follow the same phase order and proof requirements as the Apple route. Finalization removes only the three receipt-labeled volumes after evidence review. A failed or interrupted run requires inspection of its host receipt and owned Docker resources before any retry; the script does not retry silently.
