# Production check semantics on the profiled Native Store path

Source-only audit at `cb12183e`; hashes in `source-basis.json`. The saved Native DevTools episode measured the public `createNativeFrameLoop.advance → NativeRootWorkQueue.enqueueStores → root.prepareStores` path. The 32.3/30.8% owner/currentness and 12.5/12.4% host/readiness figures are disjoint *sampled-stack shares* (1,649/1,123 selected Native samples), not elapsed time or removable cost. Their code is invoked on the production Native path. The inspected runtime files contain no `NODE_ENV`, `import.meta.env`, `process.env`, or `__DEV__` condition around these guards. A separate emitted-bundle audit is needed to prove the exact shipped bytes; source alone establishes that their execution is not gated on development mode. `#activeCounters` and `#profileCounter` gate optional instrumentation, not the decisions below. The React/R3F context uses its own subscription/reconciliation/host rules; these Native guard shares cannot be assigned to React or subtracted from the Native timer to forecast parity. [Saved profile](../2026-10-22-native-devtools-profile/results.md) and [cost map](../2026-10-22-native-devtools-profile/native-cost-map.md).

**Reader and owner currentness.** A component's native `use(store)`/`useStoreAt` site has a reader ID and an accepted Store selection history for this root. Preparation chooses affected owners, captures each owner's cache/code and Store membership, and computes output for a captured input cut. `current()` checks that those same owners are alive, still have the same cache and code, still point at the same Store prop and live reader membership, and that every relevant live reader was covered. For unselected mixed inputs it checks the accepted reader receipt; for state cells it checks source, identity, version and value. The `afterHost` variant permits a newer version only under its specific captured-cut rules, so a host setter that dispatches a newer action need not erase that action. A component unmounted/reused under the same key, a Store prop replacement, a reentrant writer, or a new uncovered reader makes the old candidate unsafe. See `component_state_runtime.ts:3882–3960,4140–4185,4235–4250,4570–4650`. Store receipts bind the actual accepted history object, root epoch and root version; inspection returns `current`, `retained`, or null. `retained` is valid only where the phase allows old accepted history, not a blanket freshness pass (`async_store_runtime.ts:928–961,1308–1333`). After publication, notification acknowledgement advances the existing generation only when all live subscribed readers are current and membership, subscriptions and generation are stable. Otherwise it leaves notification work dirty (`component_state_runtime.ts:11357–11391`).

**Host readiness.** VDOM first checks that the prepared mounted nodes, keyed buckets, parent/child positions, writer function and publication version still match its target record (`vdom_snapshot_runtime.ts:4773–4845`). While applying a changed owned scalar, it checks target readiness immediately before each `setProp`; a custom setter is an observable callback and can change the next target or writer (`:4855–4950`). It then updates mounted VNodes and later checks posthost/final private currentness. This makes stale writes fail rather than silently targeting a disposed or replaced host node. It does not make arbitrary host setters rollbackable. The checked writer and target scans are real runtime protection; the same source and repair review identify repeated whole-proof work across callback-free portions that may be consolidated while keeping per-write readiness and final all-member checks.

**Failure timing matters.** An ineligible closed candidate during preparation returns null (or a blocked candidate for held resources). The direct Root flush can use its generic path; the public `enqueueStores` route requires a candidate and reports an unavailable scoped delta when preparation returns null. A blocked resource candidate is kept pending. Before any host application, a stale prepared group is discarded and the generic root queue may retry via its `onStale` policy; no accepted pointer advances (`component_state_runtime.ts:4518–4528,4930–4941`; `native_root_work_queue.ts:367–450,480–516`; `root_work_queue.ts:539–624,706–725`). Once host application starts, a thrown writer or stale posthost/final check is **not** a safe generic replay: the candidate records terminal host failure, VDOM fails publication, touched host domains are quarantined, and pending direct work is dropped. Earlier physical writes may remain; unpublished accepted history and pending action cutoffs are not falsely acknowledged (`component_state_runtime.ts:4933–4957,4991–5035`; `native_root_work_queue.ts:523–562`). After successful pointer publication, subscription/effect errors are reported as postpublication callback failures (`native_root_work_queue.ts:565–633`). Store notification acknowledgement occurs after accepted publication; a failed acknowledgement leaves the generation pending rather than fabricating a current reader history.

The repair opportunity is narrower than deleting checks: the saved plan identifies repeated prototype audits and temporary receipt creation, repeated coverage normalization, and repeated public posthost wrappers. It proposes invocation-local canonical proofs and conservative fallback for unproved/custom objects. These are candidate designs, not a measured saving or evidence that every current scan is necessary. [Reviewed proposal](../2026-10-22-native-devtools-profile/astra-repair-plan.md).
