# Realtime speed gap: remove the repeated peer proof

22 October 2026. Source review of `3dd9571167e8397de4f52ead4d78264970442ea5`, with the unexecuted HMR edits explicitly excluded from performance reasoning. **Implement one linear scalar-target preparation slice. Delete the mounted recipe's peer-membership proof; resolve current key/owner uniqueness once per candidate using the existing bucket index.** Retain the compiler, ordinary declarative authoring, immutable accepted outputs and all publication/lifetime checks. [orchestration.md](orchestration.md) gives two disjoint Sol-medium packets and one consolidated evaluation boundary.

This is a specific algorithmic defect with a concrete deletion, not another proposed cache. It is not a proof that repairing it recovers the entire speed gap. Earlier versions already lost before this defect existed. No tests, builds, benchmarks, browser workloads, servers or product edits were performed for this review. The evidence-first skill governs claim scope. Exact file hashes and claim anchors are in [source-basis.json](source-basis.json).

## 1. The new finding

`ScalarPlanFields.members` stores a weak reference and owner identity for **every node sharing a raw key, in every target's recipe** ([VDOM:224–233](../../src/vdom_snapshot_runtime.ts#L224)). Cold successor creation maps the entire bucket inside `targets.map`, allocating the peer array again for each target ([4344–4370](../../src/vdom_snapshot_runtime.ts#L4344)). Warm preparation then:

1. Compares the candidate bucket to the recipe's whole peer list for every target except the first target using that key ([4136](../../src/vdom_snapshot_runtime.ts#L4136)).
2. Dereferences and validates every member of that recipe's peer list for every target ([4140](../../src/vdom_snapshot_runtime.ts#L4140)).
3. Recreates the candidate's first strong member list by dereferencing the first recipe ([4157](../../src/vdom_snapshot_runtime.ts#L4157)).

The scene is an ordinary repeated-component pattern, not an artificial hostile-key fixture. Both `Position` and `Rotation` author `<group key="motion">`; there are 256 such component owners ([native.tsx:12–38](../2026-10-22-bound-scalar-execution/consumer/native.tsx#L12)). `carryHostKeys` preserves an explicit host key unless `scopeExplicitHostKeys` is set ([Root:1795](../../src/component_state_runtime.ts#L1795)). That flag is introduced for the particular collection-owner replacement case, not ordinary `Array.from` composition ([11798](../../src/component_state_runtime.ts#L11798)). Thus these 256 hosts share the `motion` bucket while their `componentOwner` identities distinguish them correctly.

Let `t_k` be targeted rows and `b_k` live bucket members for raw key `k`. Warm proof work is **O(sum(t_k * b_k))** rather than O(sum(b_k) + targets), with fixed per-target props/children. For the stable successful 256-row motion bucket, the two loops imply 65,536 + 65,280 peer callback iterations and the first member-list copy adds 256 dereferences: **131,072 source-level WeakRef dereference opportunities per warm preparation**, excluding the marker and required later validation. A complete cold construction of all 256 recipes creates 65,536 WeakRefs and peer tuples. These are deductions from the loops and authored multiplicities, not observed allocations, executed counters, GC evidence or milliseconds. JIT behavior and first-frame mixed cold/warm history are not inferred from them.

The prior mounted-plan review explicitly required peer proofs in recipes. That design chose the wrong scope for the fact being proved. The implementation also correctly restored a linear cold owner index after an earlier source review caught repeated filtering, but the warm path bypasses that index and repeats a larger peer proof. Passing output/lifetime tests and recording `257 warm rows` did not detect the multiplicity defect. The new regression must check both behavior and work growth.

## 2. Exact representation decision

**Delete `ScalarPlanFields.members`, all recipe WeakRef creation/dereferencing, and the peer loops in `earlyWarm`. Do not replace them with a persistent shared weak proof.** The existing candidate-local `buckets` Map already holds one live-member snapshot per key and an optional owner-to-node uniqueness index ([4103](../../src/vdom_snapshot_runtime.ts#L4103), [4164](../../src/vdom_snapshot_runtime.ts#L4164)). Use it for warm and cold targets alike:

1. On first encounter of a key, snapshot the current `#nodesByKey` Set into `bucket.members` once. If owner-qualified lookup is needed, build `bucket.owners` once from those members. Duplicate owner IDs map to `null`, exactly as the current cold branch does. Reuse this index for all subsequent rows of the key.
2. Resolve the target **before** considering its hint: singleton bucket for an unqualified region, unique `componentOwner` match for a qualified one. Missing/ambiguous target declines. A hint never bypasses uniqueness.
3. A genuine recipe may supply the immutable prop layout only when its `node` is the resolved node and its root/key/tag/componentOwner, exact accepted VNode, handle, scoped-source value, retained children and output-name order still match. Preserve all present target-local checks. Missing, forged, foreign or stale hints use cold prop preparation before host mutation.
4. Construct the same immutable next props/VNode and successor recipe. The successor retains its own target/layout/children, **no peers**. No public interface, compiler schema, Root shape field or publication method changes.
5. Keep `StorePropDeltaRecord.buckets`: it is the one-shot candidate footprint, not the cross-frame recipe. Keep its current membership validation in every existing admission and post-host phase ([4412–4487](../../src/vdom_snapshot_runtime.ts#L4412)). Keep `#isStoreTargetReady` before each changed scalar write and its exact writer/lifetime/placement checks ([4553](../../src/vdom_snapshot_runtime.ts#L4553)). Keep the accepted journal and final immutable VNode assignment ([4509](../../src/vdom_snapshot_runtime.ts#L4509)).

Why this is sound: a recipe proves the shape of its **own exact immutable VNode**. Another owner sharing its spelling of `key` does not determine that shape. Current owner uniqueness belongs to the live key index. Candidate freshness belongs to the existing candidate's member snapshot. The old recipe's peer identities duplicate neither meaning usefully. An unrelated peer inserted **before preparation** may now leave the surviving target's layout warm if uniqueness still holds. A peer inserted **after preparation** still invalidates the captured candidate under the unchanged conservative bucket rule. Duplicate same-owner peers decline even with an otherwise genuine hint.

This retains one identity/version/publication model. It adds no index authority or version counter and does not rename authored keys to disguise the problem. Expected preparation work becomes O(B + T + P + C), where B is members in distinct selected buckets, T targets, P scalar props and C retained child checks. Existing later validation traversals remain separate O(B + T + C) passes; host writes remain O(W). The current index intentionally may touch unrelated members of a selected key bucket even for one sparse target. This slice makes no O(affected targets) claim for that case and selects no persistent pair index or new container.

## 3. The comparator is doing real declarative work

The primary comparison has matching authored motion expressions, 256 retained scene objects, independent local offsets, marker epoch, meshes/materials and common drawing. Native calls `clock.dispatch` then `root.flush` ([native.tsx:64](../2026-10-22-bound-scalar-execution/consumer/native.tsx#L64)). React calls `flushSync` around a frozen external-store snapshot update; `useSyncExternalStore` delivers it to 257 component readers ([react.tsx:6–36](../2026-10-22-bound-scalar-execution/consumer/react.tsx#L6), [62](../2026-10-22-bound-scalar-execution/consumer/react.tsx#L62)). It is not the old effect-based imperative adapter.

The actual installed React Compiler output has `_c(8)` in each motion component. It retains the activation closure and static children, evaluates the three scalar expressions, and produces new group JSX when those outputs change ([transform:30–116](../2026-10-22-bound-scalar-execution/proof-canvas-v1/transforms/react/react.tsx.js#L30)). App retains its static scene tree ([134](../2026-10-22-bound-scalar-execution/proof-canvas-v1/transforms/react/react.tsx.js#L134)). Actual R3F `commitUpdate` diffs instance props, replaces its accepted prop snapshot and applies the changes ([reconciler:641](../2026-10-22-bound-scalar-execution/source-basis/r3f-v10/reconciler.tsx#L641)). It operates on the instance passed by reconciliation; it does not rediscover all other scene hosts whose local key is `motion` for each prop update.

Native already avoids those motion component bodies. Its Rust emitter now uses the shared numeric DAG/CSE backend to emit schema-2 arithmetic ([store_numeric_kernel.rs:50–112](../../compiler/oxc-spike/src/store_numeric_kernel.rs#L50)); the installed transform contains actual straight-line functions ([native transform:304](../2026-10-22-bound-scalar-execution/proof-canvas-v1/transforms/native/native.tsx.js#L304)). `prepareOwnedClosedStoreOutputs` executes them inside private capture/output buffers ([closed_store_execution.ts:410](../../src/closed_store_execution.ts#L410)). Missing memoization, an unimplemented arithmetic emitter or a missing worker is not the current explanation.

There is a real contract difference: React's application clock is just a frozen snapshot plus listeners. Native carries chronological actions, root versions, held/forked accepted histories, reader receipts, explicit transactions and partial-host failure semantics. The frame workload does not exercise all those behaviors. This is a fair **product-interaction comparison** of the chosen declarative APIs, not an identical-transaction-semantics cost experiment. Replacing React's clock with Native's Store would impose Native's extra contract on the competitor and answer a different question. No definite omitted required output or incorrectly excluded React commit was found that invalidates the current comparison.

The R3F `useFrame` arm is separate: passive input assignment plus actual v10 scheduler advance invokes ref writes without per-frame React state publication ([react-frame.tsx:35](../2026-10-22-bound-scalar-execution/consumer/react-frame.tsx#L35), [122](../2026-10-22-bound-scalar-execution/consumer/react-frame.tsx#L122)). Do not infer that all frame-hook updates traverse React scheduling, or generalize this particular v10/manual-advance result to every R3F frame scheduler. The imperative arm is another contract and is not an attainable same-semantics floor.

The harness's update interval includes the returned accepted marker lookup in every arm. Through-draw includes graph validation, rendering, allocation/readPixels/checksum ([scene.ts:163–190](../2026-10-22-bound-scalar-execution/consumer/scene.ts#L163)). It is not pure render time or physical presentation. Local controls reset before measured frames. All-dirty phase updates, alternating tiny expressions, fixed topology and local repeated keys are useful and representative of one basic declarative animation, but omit structure churn, sparse/source-selective work, ongoing local actions, resource waits, actual input arrival and coherent multi-root transactions. Baseline timing is unminified on all arms; minified/rebundled/CSP are delivery proofs. Preserve this comparison unchanged for the slice.

## 4. Why the earlier recommendations did not establish competitive speed

The previous reviews targeted real mechanisms: repeated canonical audits/empty histories, arbitrary-kernel effect boundaries, redundant owner discovery, scalar tree assembly, deferred adapters, repeated capture normalization, recursive arithmetic interpretation and previous-prop reflection. Those recommendations were implemented and their respective boundaries still lost. They do not form a matched before/after series, so their incremental savings or regressions cannot be computed from successive medians.

The conceptual mistake was treating the existence of a compiler-selected path and lower local work counts as sufficient progress toward the total budget. The runtime still performs captured input/history work, immutable authored/expanded/VDOM materialization, mounted matching, lifecycle validation, host writes and exact publication. Those costs can exceed the tiny component arithmetic avoided. The data-only route initially traded emitted arithmetic for interpretation; later work repaired that trade. The mounted reuse proposal then removed descriptor work while introducing repeated peer proofs and quadratic retained proof storage. Each local success needed an end-to-end cost model that included the new work.

The current source does **not** justify reusing older hotspots as if unchanged:

With a fixed React denominator, update parity would need 6.55 ms / 89.1% median and 7.20 ms / 88.9% p95 reduction; through-draw parity would need 6.00 / 6.30 ms. **Measured removable budget: unknown.** The peer defect has no measured phase share; the prior negative episodes prevent treating its repair as a demonstrated complete explanation. No promised speedup or new cold/memory budget is fabricated.

The selected source gate is linear candidate bucket indexing, target-local recipe validation and zero peer WeakRefs retained in recipes. The performance gate remains Native update and through-draw median **and** p95 no worse than the same-run declarative arm, with identical authoring/output/resource/timing semantics. A correct complexity repair that still loses is **algorithmic repair PASS / realtime parity FAIL**. Preserve that failure; do not dispatch a new cache/interpreter/writer just because the remaining gap exists.

The defensible product target is long-lived, retained canvas/Three scenes with compiler-known scalar dependencies, stable resource identity, ordinary declarative state and bounded structural fallback. A dependency-directed runtime can avoid work proportional to unrelated component/subtree execution and avoid repeating shared derivations; a small same-thread cut can be cheaper than reconciling them. That is where the architecture has a credible mechanism to win, supported narrowly by older fixed-topology studies, not a guarantee for this implementation. The present all-dirty, three-expression scene has little redundant computation to fuse; it primarily tests the cost of delivering changed outputs. It should at least be linear and competitive before expanding the claim.

Do not treat DAG as a synonym for a faster scheduler. The compiler already emits local straight-line arithmetic. Cross-owner fusion would require actual shared captured inputs and preserved effect/host order; independent local offsets cannot be identified merely because their current values happen to match. No worker, interpreter, adaptive container or further compiler capability is selected here. Ordinary DOM/canvas roots need not wait for each other; explicit coherent groups retain their existing contract. This repair changes neither rule.
