# r3act frame publication path: source audit

Source basis is product commit `9759a0bb3` and the installed `native-frame-publication/proof-canvas-v3` native consumer. Current product and installed consumer files have no diff from that commit. This is a source trace, not a measured phase-cost attribution. The archived proof passes 72 grouped frames with matching host state, pixels, identity, and accepted versions; it does not separately instrument the public queue's batch and validation phases.

## Selected route

The installed consumer defines a `clock` Store, 128 Position and 128 Rotation owners with one local numeric state each, and one FrameMarker. The compiler transform contains schema-3 `batchKernel` execution for all three component kinds; Position and Rotation have schema-7 retained-child host programs, while FrameMarker has schema 5. The root sets `scheduleCommit() {}`. Each harness update sets an epoch, calls `frameLoop.advance`, and requires `drawn` with a committed publication. The frame loop's `update` callback dispatches `{phase, epoch}` to `clock`; its `draw` callback increments a diagnostic counter. The shared harness subsequently validates the Three graph and calls `WebGLRenderer.render` plus `readPixels`. Thus the controller's `draw` is an acceptance barrier in this proof, not the WebGL rendering call. See [consumer](../2026-10-22-native-frame-publication/proof-canvas-v3/inputs/consumer/native.tsx) and [harness](../2026-10-22-native-frame-publication/proof-canvas-v3/inputs/consumer/scene.ts).

`advance` creates a frozen frame time, calls the user update, then `#publish` calls `NativeRootWorkQueue.enqueueStores` for the one participating root and selected `clock` Store. Its settled callback records *queue* target versions; a committed result draws only if every root's live publication version still matches. Pending or stale work does not draw. See `src/native_frame_loop.ts:169-275`.

`enqueueStores` selects `root.prepareStores`, not root `flush` (`src/native_root_work_queue.ts:196-204`). `prepareStores` calls `#prepareClosedStoreCandidate(selected, false, publicationLease, true)` (`src/component_state_runtime.ts:2454-2470`): explicit group continuation, `internalCellCapture=false`, and no output-change requirement. The private candidate routine captures an empty retained-cell list, stages selected closed Store outputs, builds a VDOM program and a normal deferred candidate wrapper (`:4414-4678`). Schema-7 local values needed by the batch come from the producer-owned World cut; this route does not rerender those component bodies for their numeric output when the passive contract holds. Eligibility is conditional; an invalidated owner, metadata, code, reader membership, retained child, or unclosed work can reject it.

The staging routine first allocates selected Store/owner/reader sets and maps, then scans **all live Store reader memberships** to select affected owners (`src/component_state_runtime.ts:3258-3438`). It checks metadata, cached output shape, Store identity, reader membership, code and retained-child/effect constraints for each candidate. Bound requests and input arrays may be reused after a prior accepted shape; the first/mismatched shape allocates frozen per-input records and bound requests. If every selected reader is covered, it seals an owned request builder and calls `prepareOwnedClosedStoreOutputs` (`:3961-4021`). Its `current` validator rechecks each affected owner and then scans the whole live reader table again for newly uncovered readers (`:3882-3960`). This is an O(R) membership pass per invocation, with R all live root reader records, even when one Store is selected. These scans enforce coverage under reentrant Store/reader changes; repeated whole-table passes are an apparent cost question, not yet proven redundant.

For the eligible owned path, `prepareOwnedFrameSchedule` groups the rows by exact verified execution and ordered Store identities, constructs per-group output columns, asks World to capture local cell columns and the Store transaction to capture shared paths, then invokes the verified batch kernel into final row arrays (`src/closed_store_execution.ts:520-617`). World captures owner lineage and cells into maps/rows (`src/owner_state_world.ts:2800-2900`); Store capture audits canonical Store shape, deduplicates shared Store/path projections, and stages direct reader rows (`src/async_store_runtime.ts:2374-2490`). `captureVerifiedOwnedScalarBatch` allocates final row arrays, executes one verified kernel per group, validates values and freezes the resulting frames (`src/closed_scalar_output.ts:266-286`). The source supports fewer per-owner expression calls and no separate transferred output scratch on this path. It still allocates schedule arrays, maps, captured rows, final arrays, immutable frames and candidate records at O(N) scale; the batch grouping itself costs O(N) plus distinct input-path work. Exact per-frame allocations and time are unmeasured here.

For schema-7 retained children, staged rows become owned frame regions and `prepareOwnedScalarStoreDeltas` can build a VDOM scalar program (`src/vdom_snapshot_runtime.ts:3709-3777`); schema 5 can use the general scoped VDOM Store-delta program. `#prepareStorePropDelta` resolves buckets and mounted targets into prepared arrays/maps (`:4365-4764`). Public `prepareStores` may receive `ownedScalarPhases`, but `validationStrategy: owned-scalar-immediate` is installed **only** when `internalCellCapture` is true. On the explicit queue path, `conservativeOwnedPrepared` and `conservativeOwnedPostHost` begin true, so the public candidate retains full VDOM `program.validate`, private prepared and post-host target checks (`src/component_state_runtime.ts:4570-4647`). This is the consequential route distinction: the immediate-flush sweep counters/shortcuts do not describe the public frame queue.

The generic `RootWorkQueue` validates the prepared candidate group and queue versions, repeats candidate validation after callbacks, claims/admit-checks the entire native group, then commits each member (`src/root_work_queue.ts:525-695`, `:726-785`; `src/native_root_work_queue.ts:332-569`). Native admission calls each public candidate `validate`, the external work validator if supplied, and private `admitPreparedNativeGroup`. After host application it calls external `validateWork`, each `validatePostHost`, each `preparePublication`, and each `validatePostHost` again before the grouped publish. Queue validation uses an O(G) root map and repeated O(G) version/validator passes (G participating roots). Here G=1; fixed queue setup still includes frozen transition/dependency arrays, root maps, publication holds, candidate/lease maps, closures, and cleanup. These are correctness gates for version/reentry/partial-host failure, not proven dispensable.

VDOM validation checks writer identity and scans keyed bucket memberships, every prepared target, retained child identities and text targets (`src/vdom_snapshot_runtime.ts:4773-4845`), O(W+C) per sweep for W writes/targets and C retained children in those targets. Public host writer lookup is a potential caller callback. During application it compares each proposed property with the previous value; for a changed owned frame property it calls `#isStoreTargetReady` before `host.setProp`, then updates mounted VNodes after all writes (`:4861-4948`). That per-write check includes writer reflection, mounted/keyed identity, parent/child and publication-version guards. Host `setProp` itself is an external callback and may dispatch newer actions or mutate another root. The queue's post-host checks preserve the captured cut; later same-lineage actions remain pending rather than being folded into the accepted frame. In a one-root proof, cross-root continuation is not exercised by each frame, although the controller and queue support grouped roots.

Grouped publication swaps Store/closed/World accepted state and increments root publication version (`src/component_state_runtime.ts:4644-4664`). Queue `afterCommit` installs subscriptions, closes transition scopes, and calls each candidate's `runEffects` after pointers and queue versions become visible (`src/native_root_work_queue.ts:567-643`). For this group route, `runEffects` notifies Store subscribers and calls `#acknowledgeCurrentStoreNotifications` (`src/component_state_runtime.ts:4664-4672`). Acknowledgement snapshots subscriptions and all live reader memberships, obtains canonical accepted reader receipts, rejects pending/blocked/changed membership, rechecks generation and membership, then advances the existing committed generation (`:11357-11391`). It is O(R+S) per changed generation (R reader memberships, S subscribed Stores), with transient arrays, objects and a Set. It prevents a subsequently scheduled generic flush from rerendering unchanged opaque readers while preserving genuinely pending generic work. It is a semantic check, though its full-table cost needs measurement.

The older internal `#tryFlushClosedStores` is reached through `flush` (`src/component_state_runtime.ts:6331-6340`, `:6498-6520`, `:7108-7145`). It may use an immediate candidate and the `owned-scalar-immediate` preflight strategy. `ComponentStateRoot.#activeCounters` is set for `flush`, not for public `prepareStores`; the explicit frame queue does not populate those counters. The installed consumer clears counters after local-control flushes, captures 72 frame snapshots, then its `dispose` control performs generic observation and a direct epoch-73 `clock.dispatch` + `root.root.flush()`. Terminal `store.batch.calls=3`, `store.batch.rows=257`, `publication.immediate.runs=1`, and one prepared/post-host sweep therefore cannot be attributed to the 72 explicit grouped frames. Their frame snapshots contain the consumer-injected `frame.group.committed`, `frame.draws`, and `frame.accepted-root-version` values, not batch/sweep counters. The schema-3 compiled programs establish availability; the source predicates establish the selected route *if eligibility holds*; the archived per-frame oracle does not independently count that branch. No timing fraction or React comparison follows from these counts.

## Cost classification and evidence limits

| Work | Source scale | Why present / open question |
| --- | --- | --- |
| Frame controller, one-root queue setup, holds and candidate wrapper | fixed for this scene, O(G) generally | Stable acceptance and resource/publication ownership; fixed latency unmeasured. |
| Initial affected-owner discovery and request construction | O(R+N) | Coverage and authentic cached-shape checks; bound requests can be reused but full reader discovery remains. |
| World/Store producer capture, grouping and batch outputs | O(N + distinct paths) | Canonical captured inputs and final immutable outputs; replaces per-owner callback arithmetic, not all row work. |
| VDOM preparation and host writes | O(W+C) plus changed props | Target identity, retained children and host effects; `setProp` and writer lookup can call host code. |
| Repeated candidate/VDOM/closed validation | O(G) queue passes plus O(R+W+C) for each relevant candidate pass | Reentry, code/lifetime/reader/target freshness. Repetition is source-visible; safety of elision is unproven. |
| Postpublication Store notification acknowledgement | O(R+S) when generation changed | Prevents generic reread of already-current opaque readers; must reject newer/unread/blocked work. |

No per-stage timers or allocation attribution exist in this proof. In particular, neither a whole-page `publishMs` nor source loop counts identify how much time is spent in validation, materialization, host writes or GC. The next evidence step is synchronized per-frame mechanism and phase attribution on the *public queue* in both React and r3act under the same installed workload, retaining failures and raw observations. This report makes no optimization recommendation pending that attribution and the planned Astra review.
