## Decision and evidence limit

Keep a dependency DAG as the *semantic relation* for known input, task, derived-value, and host-sink dependencies. It can move independent known-key request starts before render discovers them, order dependent work, coalesce shared derivations, and expose why a candidate waits. It must **not** become a graph traversed for every update or a second mutable version/publication authority. The currently qualified async frontier study demonstrates waterfall avoidance versus an intentionally serial loader: 364.4 ms serial versus 144.8 ms DAG median across 30 page blocks. React with *equal explicit preloading* is 143.6 ms (p95 152.1 versus DAG 151.2), so this is parity with a well-orchestrated React application, not a universal React limitation or async speed win ([summary](../../results/async-dag-frontier-v2/summary.json), [thesis](../../product-thesis.md)). React's reconciler does not infer arbitrary application fetch dependencies from components before they render; router/data libraries or explicit preload code can provide the same known-key concurrency. A request whose key depends on an unresolved result cannot start yet in either architecture.

## What exists now

`TaskGraphPlan` is packed source/task CSR adjacency and topological order. `TaskGraphRuntime` handles *synchronous* source writes, one queued fanout per source, topological task evaluation, and `Object.is` pruning of unchanged outputs. Its runtime-owned value array is a separate research mechanism; it is not currently the shared Store/owner/publication authority. `defineTaskGraphPlan` builds fixtures and deduplicates by `includes`; production Rust should emit the packed form rather than build it per transition. A universal CSR walk has no proven dense-frame advantage.

The async path is more substantial. `prepareAsyncTaskPlan` checks IDs, external inputs, hard task prerequisites, and cycles. `executeAsyncTaskPlan` uses unresolved counts and a ready heap, launches up to `maxConcurrency`, and starts children when their own parents settle. It reuses *completed* outputs outside changed-input descendants, isolates observer errors, and aborts a candidate; synchronous task callback prefixes still run serially on the JS thread. `createTaskExecution` snapshots task definitions and inputs, exposes one `AsyncResource` per output, and ties cancellation to that execution. `NativeTaskTransitionQueue` groups roots with equal captured inputs, restarts changed live inputs with bounded attempts and completed-output reuse, uses explicit replacement keys, and delegates grouped publication to `NativeRootWorkQueue`. The root queue prepares/revalidates candidates, holds resource/Store leases, waits on observed pending resources, and publishes through the existing native group authority. Same-root independent work is possible through the newer queue; the older coordinator's coarse overlap rule is not the whole runtime.

OXC now accepts top-level, direct `asyncTask` calls, infers literal `values.get("key")` reads, merges explicit literal dependencies, validates order, rewrites the call with those edges, and emits a semantic plan/revision via Vite. This proves narrow compiler provenance. It does not analyze arbitrary helper reads, dynamic keys, component-tree loaders, or user transaction intent. The standalone compiled-plan binder checks IDs/order, but cannot prove separately supplied callback bodies match the fixture. `AsyncResource` only observes an already created thenable, owns a one-shot 0→1 status, and reports actual reads; it neither starts requests nor owns provider cancellation. Resource-read discovery in root preparation therefore happens after execution has begun and is distinct from compiler-known task prerequisites.

## Proposed contract

Use one revisioned dependency authority with **typed relations** and physical plans selected per operation. `hard-value` means a task cannot begin until a prerequisite value exists. `source-affects` means changed input invalidates a derived result or host sink but may be pruned by equality. `read-freshness` records the Store/resource/owner footprint that must validate before acceptance. `publication-conflict` expresses overlapping root/host writes and requested group reveal. These relations can share stable source, site, owner, task, and code-revision identities while retaining different algorithms: a ready heap for async tasks, sparse fanout or prepared dense ranges for derived values, and the existing root queue for publication. Do not conflate a fetch prerequisite with a commit barrier, or encode all four as one edge kind.

For a route `workspace/:id`, start `profile(id)`, `permissions(id)`, and `recommendations(id)` together when `id` is known. Start `projects(profile.accountId)` only after `profile`; compute one shared `navigationModel(profile, permissions, projects)` when those values are ready, and fan it to both sidebar and header sinks. A ready shell may reveal under an explicit policy while a recommendations boundary remains pending. If `projects` needs a key supplied by `profile`, speculative `projects` fetch is invalid until that key is known. A changed `permissions` input should invalidate its reachable model and sinks without refetching independent `recommendations`; a shared model must be evaluated once per candidate, with per-root acceptance histories preserved. Batching means one accepted candidate/host publication for compatible ready sinks, not holding an unrelated urgent update behind the slowest branch.

Compiler output should include declared task IDs, effect/capability class (pure derived compute versus external request versus opaque callback), stable dependency fingerprints, and bounded sink footprints. Runtime discovery may add actual resource reads to a *candidate-local* frontier, validate their versions, and schedule a new ready wave; it must not silently promote an undeclared dynamic read into a static hard edge. Opaque callbacks retain generic preparation/reconciliation. For CPU-heavy pure tasks, cooperative yielding or a worker is a separate measured policy with transfer, startup, queue, validation, and stale-result costs; promises alone provide no CPU parallelism.

Reuse the async scheduler's validation/frontier, native execution's resource adapter, the Store/owner versions, and native group receipts. Retire duplicate transient dependency inference/binders only after compiler-emitted task metadata and the exact executable callback share a verified module revision. Do not add a persistent task-version registry or migrate accepted root history into the DAG. Cache ownership belongs to a named resource/provider scope: task cancellation revokes its candidate interest, not shared fetches or dispatched Store actions. Reusing an *in-flight* request across candidates requires key+input+code identity, lease counts, and cancellation after the last owner releases; completed-output reuse already exists. Forks may share transport/cache data while keeping distinct accepted Store and reveal histories. Reentry during getters/observers can change source versions before publication; final live validation and exact acknowledgement remain mandatory. HMR invalidates changed task code and fingerprints without reusing stale closures. Partial host failure still follows existing quarantine semantics; the DAG cannot promise rollback.

## Integrated migration and falsifiers

1. Specify the four edge kinds, lifecycle/identity keys, effect classes, and compiler rejection/fallback rules in one versioned semantic IR. Wire existing top-level task emission to the native task adapter with same-revision callbacks; prove literal hard edges and dynamic-read fallback using actual compiled execution fixtures.
2. Connect candidate-local discovered resource reads and derived-value sinks to existing Store/owner versions and root receipts. Add the route example with hard and discovery edges, shared derivation once, changed-input pruning, independent reveal, same-root overlap, forked accepted history, cancellation, reentry, stale code, and disposal. Retire redundant adapters only after behavior matches.
3. At the *slice boundary*, run one consolidated correctness/package gate and one bounded matched minified-production comparison, diagnostics off, balanced Native/React order, reporting update and through-draw median+p90, raw tails, request-start/settle timeline, critical path, urgent input-to-present, and accepted-view versions. Compare to React with equal router/preload orchestration and a serial control. No helper-by-helper timing or speed claim from edge counts. A hard-edge violation, wrong result/reveal, stale publication, leaked provider/lease, or regression in the named production productmarks falsifies the slice; parity or worse versus equal preload remains an honest possible result.
