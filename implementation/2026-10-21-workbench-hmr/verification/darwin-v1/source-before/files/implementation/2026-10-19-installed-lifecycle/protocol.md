# Installed authored lifecycle browser protocol

This diagnostic repeats the 18 October authored lifecycle episode with a fresh consumer of five installed `@r3act` tarballs. Native and React Compiler use separate static HTML entries and separate production output graphs. The application uses 256 keyed stateful rows, a shared numeric step, a keyed array edit, two independent pending resources, and disposal. The earlier checkout-alias observation remains separate evidence.

The replaced mechanism is the combined checkout-alias browser build. The runtime's existing root, Store, host, key, resource, and disposal authorities retain semantics; this protocol adds no mutable runtime registry or physical traversal. Its falsifier is any source/package/build drift, other-arm graph load, differing row/order/style/text/identity/lifetime, unresolved resource behavior, surviving interests, callback or inspection inside a timing interval, or an unbounded/focus-stealing browser run. It establishes no new latency or memory budget.

`prepare.mjs` freezes current source, five tarballs, installed graph, compiler, package report, transformations and per-arm assets in a new `proof-vN`. A successful `build-proof.json` has status `PASS_INSTALLED_BUILD_PROOF`, `inputLockSha256`, per-arm `assets` and `transforms`, entries `native.html` and `react.html`, and explicit separate-graph assertions. The primary reviews this captured build before the browser proof. The collector checks all recorded source, staged, installed, tarball, compiler, report, transform and asset hashes before and after each phase, and verifies the exact bytes of every served response.

Use pinned Node 24.18.0 and an unused proof directory:

```sh
/Users/mini/.local/share/mise/installs/node/24.18.0/bin/node implementation/2026-10-19-installed-lifecycle/verify-browser.mjs --proof-dir /Volumes/Depot/Developer/r3act/implementation/2026-10-19-installed-lifecycle/proof-v1 --phase proof
```

The `proof` phase writes `proof-pair-one-shot.json` exclusively. It runs one complete untimed Native then React episode in fresh pages, rejects a wrong-arm mount without creating a scene, and checks all 256 row values, order, style and text at mount and at every step 1–60. It checks row 0's local click and retained host after removing row 1, inserting row 256 and moving row 0 to the end. It observes detail ready while health still waits, then health ready, 257 row setups/cleanups, one setup/cleanup for each fallback, empty disposal and zero Store interests. It records stage snapshots and raw browser errors. It reports no update or lifecycle timing summary.

Only after the primary reviews a passing proof may the primary write `timing-authorization.json` with `status: "APPROVED_FOR_ONE_INSTALLED_LIFECYCLE_TIMING_PAIR"`, `kind: "timing"`, and SHA-256 fields `buildProofSha256`, `inputLockSha256`, `proofPairSha256`. Run the same command with `--phase timing` exactly once. It writes `timing-pair-one-shot.json` exclusively. Native runs first; each arm receives a fresh context and its own static entry. There is no warmup or favorable retry. The first application mount begins after its modules load, so it is not browser, OS, filesystem or network cold start. Each of 60 update intervals covers dispatch through synchronous commit; DOM inspection and animation-frame waits occur afterward. The receipt reports first update, nearest-rank within-page median/p95, sum, mount, edit, disposal and their measured subtotal. The subtotal excludes local click, async waiting/reveal and harness inspection; it is not episode CPU or an inherited product-gate PASS.

After timing completes, the primary may write `heap-authorization.json` with `status: "APPROVED_FOR_ONE_INSTALLED_LIFECYCLE_HEAP_PAIR"`, `kind: "heap"`, the same three hashes and `timingPairSha256`. Run `--phase heap` once. It writes `heap-pair-one-shot.json` exclusively. Fresh untimed pages force GC and preserve raw CDP `Runtime.getHeapUsage` and `Memory.getDOMCounters` responses at module-loaded baseline, mounted, updated/edited/revealed, disposed-controller-retained and released-controller. Signed baseline deltas describe whole pages, including engine, modules and application; they do not isolate allocations, establish leak absence or qualify a retained-memory budget.

Every phase uses a headless GPU-disabled browser, a 90-second deadline, signal handling, fresh contexts, exact synthetic HTTPS asset replay under `https://installed-lifecycle-proof.invalid`, and no live server or external network. A request outside the selected arm's manifest is blocked and recorded. An interrupted or failed phase preserves its exclusive receipt, partial arm stages, original error stack, cleanup errors, and context/browser closure flags. Close operations have separate five-second bounds; incomplete cleanup prevents PASS. Do not overwrite or rerun a phase for a favorable value; make a new source and proof identity if a source or harness defect requires correction. No VM or server is started and the saved one-CPU/256-MiB container and 512-MiB build defaults remain unchanged. These observations cannot establish physical input-to-presentation latency, cold setup, CPU attribution, population tails, low-memory behavior, independent-device behavior or a broad release claim.
