# Installed process and lifecycle observation

This collector repeats the complete 256-row, sixty-update authored lifecycle through five freshly installed `@r3act` packages. Native and React Compiler use separate static entries and production graphs. It preserves row values, style, text, order, local state and identity; the keyed remove/insert/move; independent detail and health reveals; effect and Store-interest cleanup; and exact Native owner cleanup. It adds separate startup, retained-heap and sampled-allocation views. No runtime registry, publication authority or physical traversal changes.

`prepare.mjs` creates a new `proof-vN` with `input-lock.json` and `build-proof.json`. The lock covers selected product source, five tarballs, the installed consumer, compiler, package report, transforms, built assets, browser launch implementation, Playwright protocol schema and the exact Chromium executable. `verify-browser.mjs` checks every recorded source/archive/package/asset hash before and after a phase and hashes every served asset body. Each phase reserves an exclusive one-shot receipt; a failure preserves the original error, partial stage observations and cleanup errors. Use pinned Node 24.18.0:

```sh
/Users/mini/.local/share/mise/installs/node/24.18.0/bin/node implementation/2026-10-20-process-lifecycle/verify-browser.mjs --proof-dir /Volumes/Depot/Developer/r3act/implementation/2026-10-20-process-lifecycle/proof-v1 --phase proof
```

`proof` writes `proof-pair-one-shot.json` with status `PASS_UNTIMED_INSTALLED_PROCESS_LIFECYCLE_PROOF` only after Native then React each complete the full episode. Each selected entry auto-mounts during module evaluation and sets `window.__r3actStartupReady` after matching initial output. The collector checks 256 rows, first/last IDs, step zero, waiting fallbacks and selected arm before considering startup ready. It then checks all 256 values at mount and every update, retained row 0 after the keyed edit, independent resource reveal, 257 row setups/cleanups, balanced fallback effects, empty host and zero remaining application interests. A duplicate mount must leave the mounted scene intact; after release, a wrong-arm mount must reject without creating DOM. This phase reports no timing or memory comparison.

After the primary reviews a passing proof, each observation requires its own authorization file, `startup-authorization.json`, `heap-authorization.json` or `allocation-authorization.json`. Its status is `APPROVED_FOR_ONE_INSTALLED_PROCESS_STARTUP_PAIR`, `APPROVED_FOR_ONE_INSTALLED_PROCESS_HEAP_PAIR` or `APPROVED_FOR_ONE_INSTALLED_PROCESS_ALLOCATION_PAIR`; `kind` matches the phase; `buildProofSha256`, `inputLockSha256` and `proofPairSha256` bind the exact reviewed bytes. Each authorized phase is run once with the same command and `--phase startup`, `--phase heap` or `--phase allocation`. There is no favorable retry or inherited qualification verdict.

Every arm in every phase launches and fully closes its **own local Chromium process**, sequentially. `openBrowser` is called without a remote endpoint, with headless mode and GPU disabled; `SELENIUM_REMOTE_URL` must be absent. CDP `SystemInfo.getProcessInfo` identifies one browser PID; the second arm must have a different PID, and the previous PID must be absent after closure. A fresh context and page are also closed for each arm. The only network surface is offline synthetic HTTPS replay of the selected arm's exact hashed assets; unknown, cross-arm and external requests fail the phase. The collector has a 90-second internal deadline and is run under a 150-second external supervisor. Signals and close operations have bounded cleanup. It never opens a focused browser or starts a server.

`startup` writes `startup-pair-one-shot.json` with a single fixed Native-first pair. The host monotonic interval starts immediately before each fresh `openBrowser` call and ends when the selected module has auto-mounted and the collector has observed matching ready output. It includes Chromium launch, context/page creation, route installation, navigation, module evaluation, controller mount and observer scheduling. It reports launch, context/page, navigation-to-ready and total raw intervals plus browser entry-body/mount marks. The locked Playwright ESM entry is preloaded once in the Node harness before either interval, so Native alone does not pay that controller-module import; neither browser nor application is warmed. Both arms still run the full untimed lifecycle afterward. There is no GC or CDP heap sampling during the startup interval, no update timing, and no p95 from a single startup per arm.

`heap` writes `heap-pair-one-shot.json`. Its first forced-GC CDP `Runtime.getHeapUsage` and `Memory.getDOMCounters` sample is taken in a blank `about:blank` page **before** navigation or application modules. Additional raw samples follow mounted output, updates/keyed edit/both reveals, disposal with the controller retained, and release of the controller. Signed deltas are relative to each arm's blank-page sample. They include Chromium engine, modules, harness-visible DOM and application costs; they do not isolate application allocations or prove leak absence.

`allocation` writes `allocation-pair-one-shot.json`. In separate fresh processes it starts `HeapProfiler.startSampling` after mount and the row-0 click, using the locked CDP schema's `samplingInterval:32768`, `stackDepth:128` and both collected-object flags. It stops immediately after the sixtieth update's validation and animation frame, before the keyed edit. The receipt archives the raw sampling profile and reports sampled bytes, sample count and largest attributed stacks. The sampling window includes controller dispatch, browser execution, DOM inspection, collector validation, RAF waits and driver overhead; sampled bytes are statistical, not exact allocated bytes, allocation counts or a rate. Unsupported CDP profiling makes the phase incomplete.

These are descriptive one-device, one-order observations. OS/filesystem cache state, browser install cost, live network, physical input-to-paint, CPU attribution, population tails, low-memory behavior, independent-device behavior and release budgets remain unqualified. The runtime's existing complete episode is the correctness control; faster or smaller observations alone never become a product PASS.
