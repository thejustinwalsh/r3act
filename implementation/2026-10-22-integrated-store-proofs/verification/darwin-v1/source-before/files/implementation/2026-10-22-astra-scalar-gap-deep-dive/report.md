# Realtime scalar gap: source review and execution decision

22 October 2026. Reviewed HEAD `d07ce015ef573845eb1af11ce5a46e0c7fa53bc9` plus the uncommitted enclosed scalar pipeline. This is a read-only architecture review, not a correctness, build or performance receipt. Only this directory's three review artifacts were written. No tests, builds, benchmarks, browser, server or VM ran. The [source lock](source-lock.json) distinguishes initial hashes, later-added inspected inputs and final drift checks.

## Decision

Close the current enclosed pipeline with its already planned consolidated boundary. Its source carries the earlier recommendation through capture, evaluation and output ownership; prescribing those deletions again would be stale advice. I found no definite new correctness blocker in the inspected integration. That is a source-review finding, not proof that the unrun regressions pass.

**Do not dispatch a data-DAG-interpreter-only slice as the solution to this speed gap.** The actual frame expressions contain no repeated compound arithmetic within an owner. Such a slice changes recursive tree dispatch into node/opcode/index dispatch; it does not deliver ordinary emitted-JavaScript execution. It may help, but the evidence supplies no reason to expect the missing milliseconds from it.

The strongest next bounded compiler capability worth implementing is **verified emitted scalar arithmetic inside the existing owned batch**: generate straight-line arithmetic at build time, verify its complete finite behavior once against the normalized host expression plan, then execute it only on private primitive buffers. This is a new, explicit verification contract; neither a function brand nor an emitted hash supplies the proof. The orchestration below gives a finite implementation and acceptance decision, including minified and rebundled installed artifacts. If that verifier or delivery contract cannot be kept sound and small, stop this candidate. Do not replace it automatically with another interpreter and call the capability delivered.

This recommendation does **not** say arithmetic is the dominant cost or that the candidate will achieve parity. There is no source-proven list of changes guaranteed to reach competitive execution. About three quarters of the committed baseline's update interval must disappear for parity with the latest declarative arm. Its causal allocation remains unknown. The proposed capability has a concrete retirement list and a falsifiable delivery requirement; its speed is still a hypothesis.

Subtracting interval medians does not isolate renderer cost. The new uncommitted pipeline inherits none of these timings.

## Compiler comparison, from actual source

The [actual React transform](../2026-10-22-ordinary-scalar-execution/proof-canvas-v1/transforms/react/react.tsx.js) uses `_c(8)` for each motion component. It retains the effect/control closure and child identity, calculates three numeric expressions in normal JavaScript, compares output values/children, and creates the next group JSX when needed. App memoizes its stable scene tree. `flushSync` drives the external-clock update. The pinned R3F reconciler still performs declarative `commitUpdate`, `diffProps`, prop-snapshot replacement and `applyProps` (archived `reconciler.tsx`, around 650–677). This is not a layout-effect hand-written Three adapter.

Native's compiler performs substantive work: module/site/revision identities, whole-owner effect eligibility, mixed Store/local inputs, retained child shape and scalar sink mapping. On the measured route it already avoids the owner bodies altogether. React memoization is therefore not an omitted feature that explains this gap. React's generated arithmetic is nevertheless more direct than Native's current execution representation.

Specifically, `store_numeric_kernel.rs::emit` emits only `{schemaVersion:1,kind:"owned-data",componentProgramId,moduleRevision}`. `main.rs` attaches that marker alongside the host expression tree. `closed_store_execution.ts::evaluateOwnedProps` walks each prop and invokes `evaluateClosedHostValue`; the numeric evaluator creates a recursive `read` function and dispatches on node kinds/operators. `numeric_expression_dag.rs` is unused by this Store emitter. It remains a source-span rewrite/CSE backend for other numeric kernels, not a ready serializable instruction IR.

The current Position expressions are `phase*.01+offset`, `phase*.005+offset*.5`, and `phase*.0001+offset*.01`; Rotation changes the three phase constants. Each motion owner performs eight binary arithmetic operations. Inputs recur, but no compound arithmetic subtree recurs across its three props. Per-owner CSE therefore mainly shares input loads here. Equal phase calculations across different owners are a separate cross-owner opportunity, with actual cut/input identity requirements. Equal offsets in this trace are not permission to identify independent local cells.

The two declarative arms have matching authored arithmetic, scene/resource ownership, output and draw boundary. Their complete consistency contracts differ: React's small frozen clock/listener object is not Native's chronological Store log, fork histories, held snapshots or explicit group publication machinery. That is a real product-cost difference, but its measured share is unknown. The useFrame arm has a different ref-mutation contract again and includes R3F scheduler advance; it must remain separate. Replacing the faster declarative comparator with the slower frame arm would not establish declarative competitiveness.

## Why recent contractions have not established a win

A sequence of negative episodes establishes that no measured version has passed realtime parity. It does not estimate the incremental saving of each patch: source, runs and React denominators differ. The source offers three concrete explanations to investigate through implementation, not measured causal attribution:

1. Removing repeated adapters leaves a substantial retained pipeline: Store observation/history, World cells, owner/reader selection, Root accepted elements, VDOM targets/previous props, live validation, host writes and publication. Zero component renders does not imply zero reconciliation bookkeeping.
2. Data ownership removed arbitrary kernel callbacks and their audit boundaries, but also replaced emitted arithmetic with interpretation. This is a tradeoff, not a free improvement. The new enclosing operation still calls the same interpreter.
3. The hot update continues through object/descriptor-rich general boundaries. In `prepareOwnedClosedStoreOutputs`, Root-created requests are copied by `closedDataArray`/`closedDataRecord`, World requests are remapped, projection requests are copied again by the Store boundary, and retained outputs are frozen. In `prepareStorePropDelta`, mounted key buckets are resolved, prior prop descriptors inspected, writes/next VNodes/child lists constructed. Some are avoidable representation costs; others carry observable accepted-view or lifetime meaning. Their counts cannot be priced as milliseconds.

Do not turn point 3 into another automatic sequence of helper cleanups. The current unit is already the capture/output contraction. Its outcome must be recorded before adding scope.

## Current integration review

The implementation uses one numeric scratch array inside `prepareOwnedClosedStoreOutputs`, the existing canonical World/Store captures and one owned region/output list. Root consumes `region.props`; VDOM asks the moved ownership authority. It no longer makes the successful route's old flattened per-row array followed by public numeric-array normalization and second scalar-region normalization.

The three-result fallback is necessary. The Store private operation returns null before pinning/reader observation; its wrapper now catches only external request-copy TypeErrors. Post-pin exceptions propagate to the enclosing batch, which returns null and causes candidate discard. A `public-required` result can therefore use the original path on an untouched transaction for Root-owned requests. Arbitrary external normalization callbacks still have no rollback promise.

World/Store phase results distinguish canonical-current, canonical-stale and public-required. Root uses a single union cut for eligible explicit scalar candidates, keeps public overrides on fallback, retains resource validation in its original position and preserves final private validation after public/host work. The no-callback argument relies on Root-owned props/rows, privately registered metadata and selected-only inputs; a future expansion to opaque/unselected/resource readers would invalidate it. Public pure-local/lane paths must retain their original scope. These points are release obligations for the current consolidated gate, not grounds to delete additional checks.

No definite new source bug was found in these inspected seams. Required pending verification includes original callback order, final stale/reentry checks, lane fallback, exact old-cut acknowledgement, output scratch lifetime, independent readers/forks, retained children, failed second writer and quarantine. Current source has not passed these new tests in this review.

| --- | --- | --- |

### The verified arithmetic contract

This proposal is stronger than checking a function's name, source hash or claimed origin. Obtain its actual source with the captured intrinsic `Function.prototype.toString`, parse **only** a small accepted function language, resolve all names to parameters or single-assignment local arithmetic, and prove ordered output expression equivalence against the privately normalized host expressions. Never execute the candidate during verification. Store the successful function in the existing execution association with its program/revision; an arbitrary supplied function with the same fields remains untrusted until this proof succeeds.

The specification returns an ordinary ECMAScript function's source when available; other callable objects without source use NativeFunction syntax. This permits a fail-closed distinction for bound/proxy/native forms; source-unavailable functions also decline. It does not itself prove purity. The purity argument comes from the complete accepted syntax and private-buffer invocation. See [ECMA-262 Function.prototype.toString](https://tc39.es/ecma262/2024/#sec-function.prototype.tostring) and [ECMA-262 function internal slots](https://tc39.es/ecma262/2023/multipage/ordinary-and-exotic-objects-behaviours.html#sec-ecmascript-function-objects).

Accept two simple parameters (input/output buffers), exact literal indexed input reads, finite number literals, the existing numeric unary/binary operators, bounded single-assignment locals, and exact ordered literal-indexed output assignments. A bounded parser may accept ordinary/arrow function wrappers, whitespace, alpha-renaming, equivalent numeric literal spellings and statement separators/comma sequencing that preserve the grammar. Optional strict directive has no arithmetic effect. It must reject every free identifier, call, `this`, `arguments`, eval, constructor, dynamic member/index, destructuring/default/rest parameter, output read, nested function, async/generator form, branch/loop, prototype operation and property other than the permitted numeric buffer indices. No regex-only proof or "unknown means safe" branch.

Compare normalized expression structure including operand order, grouping and signed zero. Permit CSE via local substitution/reference identity, not algebraic reassociation. Bound source bytes, tokens, locals, graph nodes, expansion/depth and output count. Do not use a collision-prone hash as semantic equality. A normalized local DAG supports verification without exponential substitution. Intermediate Infinity/NaN are allowed where existing evaluation allows them; final outputs retain current finite/primitive checks. For example bitwise coercion after overflow must not be rejected merely because an intermediate was nonfinite.

Invocation uses captured intrinsic apply, not the function's `.call` or `.apply`. Both buffers are fresh runtime-owned ordinary dense arrays with pre-existing writable own data elements at every permitted index; no accessors, holes, Proxy, user reference or output alias escapes. Fully populate inputs and overwrite output slots before each call. Prepopulation prevents an inherited numeric setter from intercepting an output assignment. Output results are primitive-checked and copied into the existing immutable output tuples. The function gets no World, Store, owner, host, metadata or publication handle. Unknown functions retain the current interpreted data route and cannot gain authority from a boolean.

This rests on the runtime's existing unmodified/captured-intrinsics initialization assumption, not sandboxing hostile code that replaced intrinsics before module initialization. Ordinary cross-realm functions with verified source can be safe because accepted code has no free realm-dependent references and receives caller-owned buffers; a conservative implementation may decline realms it cannot verify. A proxy/bound/revoked callable must decline without calling it or its overrides. After registration, mutating properties on the function cannot change its internal code; retained invocation must not consult them.

### Packaging, CSP and HMR are part of the capability

Do not serialize a function string and compile it at runtime. No `eval`, `new Function`, blob/script injection or CSP relaxation. Rust emits ordinary module JavaScript. Verification parses existing source only.

The current build is unminified, so this review establishes **no minifier feasibility**. Require actual fresh installed artifacts through the pinned default production minifier and one consumer rebundle, with proof that the verified route is selected and outputs remain exact. Name mangling is handled by lexical alpha normalization. Source transformations outside the finite grammar decline to existing interpretation; semantically valid but reassociated constant folding may decline too. That conservative fallback is valid behavior, not successful optimization delivery. Do not disable minification or weaken verification to pass this check. Do not claim arbitrary bundler compatibility.

Missing/invalid optional kernels should retain valid data metadata; malformed semantic host programs still fail under current rules. Old schema-1 markers continue working. HMR/module retirement revokes execution through the existing component/module revision association and owner lifetime, including already prepared candidates. A changed function or stale descriptor cannot be attached merely by copying IDs. Source availability and supported transform forms should be diagnosable once at registration/proof time, with no hot-path logging.

## What to retire, and what to preserve

The selected successful path retires recursive `evaluateClosedHostValue`/`evaluateClosedNumericExpression` calls per sink and their per-expression dispatch/closure work. A single verified call per owner computes all ordered scalar outputs into reused private scratch, followed by the existing finite result check and owned tuple producer. Compile-time CSE applies where actually present. It does not reorder owners to manufacture long runs: the installed motion programs alternate, so the old same-program range batching had one owner per run. Do not claim automatic loop fusion across them.

The existing normalized host program remains the semantic authority and fallback recipe. The existing association owns derived executable proof; no second mutable identity/version/publication registry is added. World/Store capture, independent reader observations, Root accepted histories, VDOM targets/journal, host writer order, exact acknowledgement, lifecycle, group claims and final live validation remain. A verified arithmetic call is passive only because the entire accepted function language cannot observe or mutate external state. If that premise is incomplete, retain the public callback route; do not merely suppress audits.

The deeper architectural direction, if this still loses, is a **mounted scalar execution plan under existing VDOM/Root ownership**, not progressively more arithmetic interpreters. It would have to replace repeated mounted key/shape discovery and generic prop-description reconstruction while keeping exact current VNode/child/history guards and necessary candidate outputs. Existing `ComponentCache.closedStoreOutputShape`, `MountedNode`, `#nodesByKey` and `#storePropDeltas` are the seams. Such a migration requires a complete consumer/invalidation map for mount, keyed moves/replacements, HMR, generic fallback, snapshots, held/fork histories and disposal. This review has not completed that proof or identified a performance budget, so it is **not dispatch-ready**. Lazy accepted-output materialization and persistent writer caches must not be slipped into the selected unit.

A negative boundary result closes this compiler hypothesis as a demonstrated parity solution. It leaves product work open, but does not authorize indefinite source-only claims about the unallocated residual. Full HMR delivery, structural/reveal scope, cold/memory and independent-device evidence remain outstanding.

## Which research wins still apply

The notebook and paper support direct source-to-sink work for stable scalar topology and avoiding unaffected owners. Those mechanisms already matter here; Native's zero owner renders is evidence that one major idea is present. Historical direct writers beat an interpreter on one fixture, making emitted arithmetic a plausible mechanism, not a transferable percentage saving. Experiment V found field representation more consequential than compiled adjacency and charged higher setup to compiled edges; this cautions against assuming a larger IR is a win.

Sparse/clustered/dense and bucket studies establish workload-dependent crossovers. They provide no threshold or storage selection for this 257-owner all-dirty canvas episode. Keyed bucket wins concern local structural work, not dense scalar arithmetic. Async frontier work overlaps ready I/O and matches equal React preload; it is unrelated to main-thread numeric fusion. Fixed-topology Snake wins and lifecycle studies retain their archived source/interval limits; the qualified dense DOM FAIL remains FAIL. Recording A's unresolved causal ledger is exhausted, not a prerequisite to another recording loop. Human maintenance participants remain zero; no maintenance superiority follows.

The realtime product should permit independent DOM cadence and publish the canvas root before its intended draw. Explicitly requested DOM/canvas groups still use coherent managed acceptance. Removing optional cross-host grouping does not remove single-root source freshness, old accepted reads during host application, exact action acknowledgement or partial-failure handling. These meanings need efficient representations; neither semantic requirements nor current implementation overhead can be assigned the entire speed gap without evidence.

### Why this candidate instead of a template library

Runtime-owned finite templates have a simpler trust story and should remain an option for a small, deliberately documented expression family. But arbitrary composition of binary/unary operator templates is another interpreter (or a tree of function calls); a tiny hand-picked set covering this benchmark's constants is fixture specialization, not the requested ordinary compiler capability. Enumerating enough whole-expression templates adds a separate evolving grammar and matching surface. The finite source verifier instead checks the exact compiler-supported numeric language against the already normalized expression authority and lets the JavaScript engine compile straight-line code. It earns its complexity only if the verifier stays restricted, production artifacts select it and the integrated result justifies it. Those are hard gates, not assumed advantages.

The verifier must not become a general JavaScript parser. No general statement execution, control-flow proof, algebraic optimizer or arbitrary minifier equivalence engine is requested. Unsupported source forms decline. For schema-5 programs, string/boolean/null literal sinks remain literal outputs in their original positions; the verified function writes only the numeric sinks, whose dense indices are derived from the normalized host prop order. Numeric-only eligibility prevents string arithmetic and observable coercion. A function's output-buffer assignments remain private preparation; moving pure arithmetic earlier within that bounded call is permitted, but published host-write order is unchanged.
