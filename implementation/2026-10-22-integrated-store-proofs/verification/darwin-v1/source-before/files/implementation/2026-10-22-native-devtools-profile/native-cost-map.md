# Native public-frame source cost map

Source-only map for the installed `proof-canvas-v3` Native asset. This is an ancestry guide for the requested DevTools profile, not phase timing or a speed forecast. The frozen bundle is `native-B0ltTLHF.js` (SHA-256 `bbdf70d9a56b64ed506966512f28689341095a26d738bbb43d8931e8ef9f9ef0`); generated line anchors and source counterparts are in [source-map.json](source-map.json). The selected arm is `createNativeFrameLoop.advance` → `NativeRootWorkQueue.enqueueStores` → public `root.prepareStores`, with `internalCellCapture=false` and `groupContinuation=true`. Direct `root.flush` and terminal epoch-73 counters describe a different path.

## Already shared with React's effective pattern

Both systems retain the static child/resource tree and change only 256 motion groups plus a marker. Native's eligible closed path does not rerun those component bodies for numeric output. It captures local World and Store inputs, groups verified execution by exact ordered Store identities, runs compiled batch kernels into final frames, and publishes once before the frame controller permits draw. The installed transform contains three kernel programs covering 257 owners. React schedules 257 subscribed leaf functions under one synchronous flush; Compiler caches stable children/effect inputs but recomputes the changing motion expressions, then R3F diffs/applies up to 769 scalar writes. The separate timing audit confirms those React writes finish inside its update timer. Neither side has a missing static-tree memoization explanation. The installed per-frame Native oracle establishes output/publication, while the terminal three-kernel counter follows a later direct flush; profile ancestry can establish execution but does not turn that counter into 72-frame frequency evidence.

## Surviving Native work to classify in the profile

1. **Frame and queue envelope.** `native_frame_loop.ts:169-275` freezes frame time, checks selected roots/versions and creates a queue handle. `native_root_work_queue.ts:196-204,332-643` plus `root_work_queue.ts:525-785` allocate root maps, candidate/lease/hold records, closures, frozen transition/dependency arrays, and repeat candidate/work/version validation at admission and after host callbacks. These are generally O(G) for G roots; this scene uses one. The public queue and controller protect delayed completion, multi-root acceptance and draw ordering. Sampled queue time can include its child Root/VDOM calls; inclusive frames must not be added as exclusive costs.
2. **Affected-owner discovery and retained-shape preparation.** `component_state_runtime.ts:3258-3438` creates selected Store/owner/reader sets/maps, scans live Store readers, checks owner/cache/code/membership/retained-child constraints and forms 257 candidate rows. Bound request/input records may be reused after an accepted shape; candidate, selected-set and schedule storage still exists per preparation. `:3882-3960` defines `current()`: it revisits affected owners and scans the whole live reader table for uncovered readers. Its calls from prepared, admission and posthost predicates can repeat an O(R+N) proof, depending on actual branch/short circuit. The first pass establishes coverage; later passes protect changed memberships, code and reentry. The cost of each is unmeasured.
3. **Producer input capture and batch output.** `closed_store_execution.ts:520-617` builds scheduled rows, execution/Store-identity tries, group input columns, a sealed schedule, World/Store projections, final row objects and frames. `owner_state_world.ts:2800-2900` captures owner lineage/cell rows. `StoreRenderTransaction._readOwnedClosedProjectionBatch` (`async_store_runtime.ts:1641-1759`) checks transaction shape, traverses projection requests, creates Store capture/projection/snapshot/direct-reader maps and fills shared input columns; its public schedule wrapper is at `:2374-2388`. `OwnedScalarBatchRows` (`closed_scalar_output.ts:207-263`) allocates each result row and per-slot property before the kernel, then `adopt` validates each output slot and creates a final owned frame. `captureVerifiedOwnedScalarBatch` (`:266-286`) executes the kernel and freezes the frame array. These constructor/adopt loops are separate from kernel arithmetic in a profile. This retires per-owner expression calls and scratch transfer, but O(N) schedule rows/maps, captured input rows, result row arrays, immutable output arrays/objects and validation remain. Allocation/GC attribution needs the fresh trace; source counts are not bytes or milliseconds.
4. **VDOM target preparation and repeated whole-target scans.** `vdom_snapshot_runtime.ts:3709-3777,4365-4764` resolves keyed buckets/members and mounted targets into maps/arrays and prepares old/new frame records. `#isStorePropDeltaCurrent` at `:4773-4845` checks writer identity, keyed membership, target node/parent/child/retained-child identity and publication state. The public candidate's `validatePrepared`, admitted continuation, `validatePostHost`, and final private predicate in `component_state_runtime.ts:4570-4650` can each reach a target sweep. `owned-scalar-immediate` preflight is only installed for `internalCellCapture=true`; it must not be credited to this public path. Some checks repeat unchanged data inside a callback-free interval, but host writers and descriptor reflection may reenter, so no whole-sweep deletion follows from source alone. Crucially, `finalGroupCurrent` ends with `program.validatePostHostPrivate()` for owned scalar phases.
5. **Host application.** `vdom_snapshot_runtime.ts:4855-4950` compares each proposed scalar with old frame values, checks `#isStoreTargetReady` (`:4918-4950`) before each changed owned write, calls host `setProp`, then updates mounted VNodes. For 769 changing scalars this can mean 769 readiness checks and host calls; exact per-frame count belongs to the new trace. Writer lookup/reflection and host calls are callback boundaries. The checks protect writer identity, mounted target/parent, host generation and publication version if a writer dispatches a newer action or mutates a host. React also performs actual R3F diff/path resolution and writes, so classify Native host cost against that obligation rather than calling all writes overhead.
6. **Store accepted-state publication and notification acknowledgement.** `component_state_runtime.ts:4653-4675` publishes Store/closed/World pointers, increments the existing root version, notifies, then calls `#acknowledgeCurrentStoreNotifications`. `:11357-11391` allocates subscription/readers arrays, per-reader `{id,membership,stores}` objects, copied membership arrays and a `seen` Set; it checks blocked readers, live membership, subscriptions, generation and current accepted history. Each receipt pair invokes `AsyncStore` canonical-shape checking twice (`async_store_runtime.ts:928-961,1248-1260,1308-1333`), producing 514 full prototype/instance audits and 257 frozen temporary receipts for 257 one-Store readers on a successful pass. This duplicate is source proven and sampled in the earlier CPU study. The history/stamp, root epoch/version, root membership, blocked-reader and generation checks are required; repeating the same prototype audit and constructing a receipt only to inspect it immediately are the narrower redundant mechanism. Accepted histories remain authoritative in Store; Root remains authoritative for live membership and notification generation.

The earlier disposable prototype-audit ablation is intentionally unsound and did not close the gap. Its 3.55/6.05 ms Native medians varied substantially, versus 6.85/8.40 ms original and 0.70 ms React in that episode. These are controls with JIT/order uncertainty, not savings estimates. The existing public-frame comparison remains a descriptive parity failure, and the React timer audit establishes a synchronous property-update boundary without an exact Native residual decomposition.

## Guarded repair order after the profile is reviewed

First classify exclusive DevTools samples and allocations under the exact public `advance` ancestry, keeping preparation, VDOM validation, host writer, queue and acknowledgement separate. A high inclusive parent count is not a removable budget. Check whether retained row/target allocation, repeated Root/VDOM scans, or host application survives materially after the known audit leaf; preserve deoptimization/GC evidence if available.

The first already specified code candidate is a **Store-owned, invocation-local cohort acknowledgement**: normalize inputs outside its passive interval; freshly audit canonical prototype and each distinct real Store once; directly inspect existing private accepted reader histories/stamps; return a result to Root, which still rechecks membership/subscriptions/generation before advancing its existing acknowledgement. Any subclass/Proxy, altered descriptor, ambient intrinsic or unproved callback dependency declines to the defensive path. No token or canonicality cache survives a callback. This removes only repeated shape audits and immediate receipt objects. It cannot be presented as a full speed fix until a semantics-preserving implementation and a measured comparison exist.

If a new profile shows a material residual in another named pass, design its replacement only around the invariant it currently guards: owner/reader coverage at preparation and changed membership at publication; VDOM target/writer/lifetime at admission and after each host callback; captured-cut/newer-action lineage and final all-member group publication. Retire a repeated scan only after proving an existing version/claim covers the same interval, with generic fallback on stale or unsupported shapes. Do not add a parallel identity/version registry, weaken Store accepted histories, move publication before host success, or infer callback-free status across a host writer. A measured budget and falsifier are still needed before selecting that physical change.

Profile limitations: line positions refer to the frozen generated bundle, not a rebuilt checkout; generated names may appear under parent closures. Source loop sizes establish work shape only. Samples, allocated bytes, deopts and elapsed update intervals have distinct denominators and must not be interchanged.
