A Deno Jupyter research project and product prototype for a pure-JavaScript,
VDOM-first JSX runtime. Its thesis is that compiler-known ownership and data
dependencies can make ordinary declarative updates cheaper, async transitions
easier to coordinate, and new rendering hosts easier to add. This remains a
hypothesis to prove against optimized React on representative workloads.

## Native authoring requires compilation

The compiler is part of the library. Use the composed Vite entry point:

```ts
import { defineConfig } from "vite";
import { nativeModulePlugin } from "./compiler/vite_native_plugin.ts";

export default defineConfig({ plugins: [nativeModulePlugin()] });
```

Supported TSX modules importing `native_runtime_api.ts` are discovered and
compiled automatically. No `@native-ui` marker, JSX pragma, or manual factory
import is required. Rust produces owner/read/task plans; module-local OXC
lowering emits JavaScript and composes source maps. Ordinary React modules stay
on their own pipeline. Mixed projects currently need a React Refresh exclusion
for native modules, as shown in this project's Vite config; that integration is
not yet automatic. Accepted native HMR currently remounts with explicit cleanup;
edit-stable state preservation remains a separate requirement. A private,
platform-specific package artifact now includes the compiler binary; it is not
published. See [native package integration](./native-package-integration.md).

### Compiler-generated host JSX declarations

The Vite compiler entry can emit JSX extensions for a host's public constructor
namespace. For a Three namespace exported from `src/scene-host.ts`:

```ts
nativeModulePlugin({
  jsxHosts: [{
    namespaceModule: "./scene-host.ts",
    intrinsicMapModule: "@compiled-ui/runtime/three",
    intrinsicMapExport: "ThreeIntrinsicElements",
    jsxImportSource: "@compiled-ui/runtime/three",
    declarationFile: "src/host-jsx.d.ts",
  }],
});
```

Generation runs when Vite resolves its configuration, for development or builds.
Include `src/host-jsx.d.ts` in the application's TypeScript project and use
`jsxImportSource: "@compiled-ui/runtime/three"` for Three-authored TSX. Relative
module specifiers in the registration resolve from the generated declaration
file. The runtime host must use the same exported constructor namespace.

The generated file references the namespace's types, so editing constructor args
or instance props changes checking without regenerating a prop catalog. Both
`jsx-runtime` and `jsx-dev-runtime` are augmented; no runtime JavaScript is emitted
by declaration generation. TypeScript/tsgo performs inference and checking;
Rust/OXC remains the runtime plan and transform compiler. Generate once before a
standalone type check on a fresh checkout, or check in the generated declaration.
The plugin leaves identical output untouched and rejects overwriting an authored
file. Remove old generated files when removing or renaming registrations.

Other hosts supply their own generic intrinsic-map type through the same
registration. The map defines supported constructors and prop conversion types;
the generator does not infer attachment, disposal or event policies. This first
implementation uses explicit host registrations, rather than discovering
arbitrary runtime `namespace` expressions. Use separate JSX import sources for
hosts with conflicting tag names; there is no global JSX augmentation.

`compiler/vite_host_jsx_test.mjs` checks generated declarations against real TSX
with production/development JSX, inferred custom constructors and refs, invalid
props, live namespace edits, and an independent non-Three host.

## Native resource boundaries — 12 October 2026

The current authored API is `use(store)`, `use(promise)`, and `use(resource)`.
A Promise stored as a value is returned unchanged: `use(use(store))` explicitly
unwraps it. Rust supplies lexical read and Suspense identities. Conditional
reads use those identities; repeated reads inside loops/callbacks remain outside
the supported compiler syntax.

The [resource workbench](https://async-transition-stress.localhost:1355/native-resource-boundaries.html)
is real [authored TSX](./src/browser/native_resource_boundaries.tsx): sibling
resource reads, startup fallback, automatic grouped publication, editable drafts,
urgent updates, overlapping loads, local rejection/retry and explicit cancellation.
Providers start in event/domain code. Boundary traversal observes reachable
siblings; it cannot discover children behind a parent that has not produced them.

Private owner/store branch journals prevent suspended work from publishing
state or lifecycle changes. Retained content is re-evaluated against current
pinned inputs; the queue retries fresh candidates when resources or dependencies
change. Cancellation abandons queue work; the domain owner controls providers,
transition scopes and compensating actions. Source/build evidence is preserved

## Native store and collection primitives — 12 October 2026

The public author surface is now `import { use, createStore,
createStoreSelector }` with `use(store)`; the compiler lowers that call to
`useStoreAt` using compiler site IDs. `useStore` remains temporary compatibility
surface. The root store uses built-in `AsyncStore`/`StoreSelection`, supports
multiple dependencies, stages private subscriptions with candidate history,
and tracks root-local notification generations. `use(store)` reads ordinary
store values; if a store contains a Promise, that Promise is returned unchanged.
Direct `use(Promise)` and automatic resource suspension are not implemented,
and resource Suspense and transition orchestration are not integrated into the
native root queue.

An advanced adapter may export `storeDependencies` and declare the complete
`StoreSource` dependency graph it reads. Render transactions discover and pin
those stores before evaluating the adapter, and reject undeclared reads or
dependency cycles. This extends adapter support without changing the ordinary
author API (`use(store)` and selectors); it does not make undeclared custom
sources readable.

The native store execution check now covers two simultaneous transitions and

## Current conclusion

The evidence supports a narrower claim than “a better React” today. Keeping JSX
and a retained VDOM while compiling source-to-region/prop dependencies can cut
repeated update work on stable UI shapes. For per-frame props, columnar and
sparse VDOM paths beat the tested React + Compiler baseline on several
fixed-topology, same-device page-load comparisons. The lifecycle-inclusive V1
now confirms that, for the preregistered 300-update episode, mount and teardown
do not erase the columnar path's advantage: paired total-cycle medians were
0.508× React at 512 segments and 0.513× at 1,024. Columnar mount cost remains
higher and small update timings are near Chrome's clock resolution. A later
45-page cadence study finds a narrow missed-slot advantage under heavy load:
at 8,192 segments, four of five pairs favor columnar VDOM, but late callbacks
only fall from 100% to 96.3% and RAF p95 remains 66.6 vs. 66.7 ms. All arms are
severely overloaded, one columnar page has an 11.6-second callback gap, and
there are no display-presentation timestamps. This is not evidence of smoother
presentation. Exact dirty-row dispatch also loses to dense or bucket scans on
some clustered/dense workloads. The sound design direction is a
workload-sensitive update plan, not “always walk the DAG” or “always diff the
whole tree.”

This does **not** yet establish smoother presentation, a general React speedup,
easier maintenance, or a replacement runtime. Structural edits remain a clear
counterexample: in the full 10,000-row stateful benchmark, React + Compiler
medians were 4.9–11.85 ms while the optimized delta-index runtime measured
12.0–39.85 ms. Delta index maintenance did beat subtree rebuilding on nearly
every operation, but those local gains did not close the end-to-end gap. The V1
keyed-owner reuse study cuts same-key rotation time by 43.6% versus generic
owner expansion (10.75 to 6.15 ms median of page medians), yet still trails
React + Compiler (5.10 ms); edge replacement regresses 17.9% against generic and
fails its guardrail. The V2 token path improves rotation over its generic
runtime arm, but its Vite selector does not include the V2 module, so its React
comparison is not verified as compiler-optimized. The separate V3
production-browser comparison uses explicit React Compiler evidence: rotation
measures 4.70 ms for token-delta versus 3.60 ms for React Compiler; edge
replacement measures 12.05 ms versus 3.50 ms. Together these results support
narrow compiler-proven fast paths while showing their membership-change fallback
must also be cheap. Async transition studies validate useful consistency
behavior but show no completion-time advantage. The prototype is still a narrow
compiler/runtime slice, not a general TSX compiler or ecosystem-compatible
renderer. The teardown-inclusive result covers only one fixed topology and 300
measured frames; page-load/compile costs, dynamic topology, cross-device
replication, developer comprehension, transitions, worker scheduling, display
presentation, and the React adapter remain open. The 30-page Long Animation
Frames follow-up found similar high-load RAF p95 across arms; its >50 ms
threshold and coarse phase fields do not explain the callback gaps or measure
display presentation. See [paper §8.16](./paper.md#816-long-animation-frames-phase-attribution-snake-frame-phase-v1)
and the [phase summary](./results/snake-frame-phase-v1/summary.json). A keyed
bucket mechanism experiment shows bounded local slot work across 1,000–50,000
rows against both a plain array and an indexed flat array. For 50,000-row
head/middle moves, the indexed array rewrites roughly 50,000–100,000 key-index
entries per operation while bucket reindexing remains local. This supports
buckets as a promising data structure, but it still does not address the
runtime's owner and host scans or provide React performance evidence. See
[Experiment AT](./paper.md#817-keyed-region-buckets-bounded-ordered-edits) and
[Experiment AU](./paper.md#818-bucketed-regions-versus-an-indexed-flat-array).
New architecture/backend research remains paused. Bounded product integration
follows the [implementation plan](./library-implementation-plan.md), while the
prepared developer study and independent-device replication remain claim gates. The comprehension
study remains pre-data, so there is no evidence yet that this runtime is simpler
to extend. For structural performance, the next discriminating work is one
integrated runtime path that avoids the observed owner and host scans, then
faces the same React Compiler product gate.

## Architecture under evaluation

- Keep the VDOM as the retained, inspectable description of output and
  structure.
- Keep a compiled dependency DAG alongside it, mapping state/trait reads to
  derived work and affected VDOM regions.
- Store hook state as ECS traits keyed by component entity and compiler-assigned
  call-site ID; use keyed child scopes for repeated hook sites.
- Use the dependency DAG to narrow reevaluation and reconciliation, with generic
  keyed reconciliation for dynamic structure.
- Keep graph, dirty-region scan, and dense propagation paths because the
  measured winner depends on workload density and locality.
- Keep JSX props declarative; `VDOMSnapshotRoot` retains a keyed tree and
  follows scalar source-to-prop bindings without re-executing components.
  OXC-emitted CSR binding IDs now feed the retained VDOM path; mount resolves
  them to host writers, while runtime-discovered bindings remain a baseline.
- Use a typed dependency/task DAG plus a versioned scheduler; boundaries choose
  keep-previous, inline-pending, fallback, or progressive reveal. Candidate ECS
  state and effects commit atomically with the VDOM according to policy.
- Keep the runtime pure JavaScript for now; add Wasm/SIMD only if profiling
  identifies a worthwhile numeric kernel.
- Expose a small host adapter boundary for DOM, Three.js, and other targets.

The current OXC spike parses a narrow TSX subset and emits repeated-host plans.
A plan can now validate and route scalar updates through a retained VDOM, but it
does not compile arbitrary JSX, dynamic keyed topology, lifecycle, or a full
dependency graph into the transition coordinator. OXC is a compiler direction to
evaluate; TypeScript remains the type-checking authority.
