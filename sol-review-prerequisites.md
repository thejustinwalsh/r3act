## Why the maintenance prerequisite does not pass

**1. There is no matched comparative maintenance observation.** The extension fixture proves discoverable mechanics to an AI implementer, followed by successful execution. There is no frozen R3F counterpart, matched starting context, participant-time record, clarification/help log, blinded patch assessment or maintenance change on both systems. The existing human study is uncollected and covers different tasks. `library-implementation-plan.md:442,461–463` requires independent developer/adoption evidence and expressly limits the pilot to its tasks. One AI fixture cannot close it.

**2. R3F already provides the public extension path being contrasted.** Its `packages/fiber/src/core/reconciler.tsx:89–101` exports `extend`, and lines 168–179 instantiate catalogue constructors and apply props. `utils/props.ts:234–338` supplies generic property application, copying/setting and direct or dashed property resolution. A user-defined geometry's ordinary `mode` property generally needs no new R3F property writer. A comparison that requires native public registration but forces the R3F author to edit private host config would misstate R3F's actual extension cost. The task must specify equivalent observable behavior and allow each system's normal public API.

**3. Some complexity is removed from the host author; substantial complexity is owned elsewhere by this project.** Native's `VDOMHost` is small (`src/vdom_snapshot_runtime.ts:65–81`) and the Three adapter has no React/Fiber import. In the pinned R3F source, Fiber ref cleanup/alternate handling is explicit at `reconciler.tsx:30,322–334`; reconstruction uses Fiber sibling/flags at lines 474–506; an internal ReactContext cast appears at lines 561–565; React-version integration callbacks occupy lines 603–668. Avoiding that dependency is a real, inspectable architectural benefit for this host author.

However, native owns keyed matching/mount/remove/disposal/ref staging in `vdom_snapshot_runtime.ts`, owner preparation/state/effects/candidate publication in `component_state_runtime.ts` and `owner_state_world.ts`, and coherent root/store/task scheduling in `native_root_work_queue.ts`, `root_work_queue.ts`, `async_store_runtime.ts`, `native_task_execution.ts` and `native_task_transition.ts`. The Three adapter itself owns attachment stacks, default capture, resource classification/disposal and events. Compiler ownership includes module discovery, Rust/OXC lowering, source maps, emitted owner/site/writer identities and Vite lifecycle. The plugin even builds and runs its own Rust compiler process (`compiler/vite_native_module.ts:301–365`). A rendering-host bug can span that machinery; the callback count does not price it.

I followed the local import/export closure from the Three entry to **19 source modules**, including the production `component_state_runtime.ts` and `vdom_snapshot_runtime.ts`, rather than attributing historical `*_v2`/`*_v3` experiments to the product. That is a conservative source inventory including type imports/reexports, not a bundle-size or hot-path count. Tree shaking may exclude unused exports. It establishes obligations to inspect and attribute, not a cost score. Conversely, R3F maintainers do not maintain the entire React reconciler implementation: they borrow it and maintain their integration/version coordination. Charging all React source to R3F while excluding native's owned generic renderer would bias the comparison in the opposite direction.

**4. Supported scope differs materially.** Native args/object/attachment identities require keyed replacement (`three_host.ts:153–180`); R3F automatically reconstructs args/primitive changes (`reconciler.tsx:483–506`). Native enumerates supported prop writers (`three_host.ts:153–213`); R3F has generic property/value handling and texture behavior (`utils/props.ts:68–94,295–360`). Native supports direct property resource attachment; R3F supports indexed/path/function attachments (`utils/props.ts:113–149`). Native rejects material arrays (`three_host.ts:475–476`) and omits hover/capture/missed/bubbling policy; R3F implements these in `core/events.ts:117–360,424–446,493–605`. React portals, offscreen hide/unhide, scheduling priorities and ecosystem compatibility are additional R3F obligations, not demonstrated native equivalents.

None of those missing features alone means the bounded host is unsuitable. They mean that a lower cost for a smaller feature set is not evidence that the same maintained renderer is easier. A fair result must name its supported slice and account separately for the features removed from the task.

## Concrete prerequisite-scope defect

**[P2] Normal Three subtree disposal silently loses resource cleanup errors.** `src/three_host.ts:428–442` catches errors into an optional array defaulting to `[]`. The ordinary node-disposal overload at lines 635–638 calls `releaseHandle(handle)` and discards that array. Generic native disposal correctly tries to aggregate host exceptions (`src/vdom_snapshot_runtime.ts:312–318`), but cannot aggregate an error the adapter swallowed. Full `host.dispose()` passes and checks its array, creating different observability depending on how the handle is released.

I reproduced this through public APIs with a registered `BufferGeometry` subclass whose `dispose()` throws a sentinel error, mounted as a mesh resource child, followed by `createThreeNativeRoot(...).dispose()`. Result:

```json
{"disposeCalls":1,"threw":false,"sceneChildren":0,"diagnostics":{"createdResources":1,"disposedResources":1,"liveResources":0,"liveHandles":0,"eventRegistrations":0}}
```

This does not show an ordinary-resource leak: disposal was attempted once and host bookkeeping was cleared. It shows that the caller gets successful teardown and the diagnostic counter reports disposed despite a failing custom cleanup. Existing normal Three fixtures pass; generic disposal-failure tests use memory hosts and do not catch this adapter-specific gap. Decide/document whether errors must surface, preserve traversal and exact-once behavior, then add a focused actual-Three regression. R3F's `disposeOnIdle` deliberately catches disposal exceptions too (`reconciler.tsx:258–271`), so this is not evidence of R3F superiority; it is a missing native error contract that a maintenance comparison must expose.

## Finite next proof

A perpetual long-term study is not necessary to make the next decision. Freeze one **bounded host implementation/maintenance comparison**, with these deliverables and a stop after collection:

1. **Freeze equivalent scope and starters.** Preserve both source/build revisions, documentation and runnable scenes. Use the proven native slice: construction, supported transform/material/custom scalar updates and reset, keyed identity/replacement, direct pointer dispatch, raw refs, owned/borrowed resource cleanup and teardown. Keep renderer/camera/bootstrap and dependencies already configured equally. Enumerate excluded R3F behaviors above. Let R3F use `extend` and generic props. For the constructor-change task, require equivalent resulting object/resource lifetime while allowing documented keyed replacement or automatic reconstruction; record any application burden rather than hiding it.
2. **Run three matched tasks with six independent developers.** Task A: implement the custom geometry/property slice from public docs, including reset and cleanup. Task B: diagnose and repair one equivalent seeded attachment/lifetime regression, with retained sibling identity and disposal/ref acceptance cases. Task C: adapt to one predeclared host-contract or Three-version change affecting construction/props/cleanup, then run both unchanged scene acceptance suites. Counterbalance arm/task order and match prior React/Three experience. Pilot instructions once, then freeze them. Cap each task/arm at 40 minutes; report timeouts as censored. This is 36 scored task attempts, not an open-ended recruitment target.
3. **Attribute displaced work.** Preserve patches, failed checks, hands-on time, help requests, misunderstood concepts and a trace from author source through compiler/kernel to host commit. Record adapter, app, generic runtime/scheduler and compiler changes separately. Reviewers must explicitly account for native-owned generic machinery and R3F's borrowed reconciler/version coupling. A public-only app extension alone cannot stand in for a renderer maintenance task. For the seeded bug, use equivalent observable defects and disclosed locations/allowed edits; do not force artificial private edits in either arm.
4. **Freeze the decision rule before looking at results.** A recommended bounded criterion is correctness in every final accepted patch, no unresolved runtime-only lifetime defect or extra native timeout, a median paired native/R3F time ratio **≤0.80** across correctly completed tasks, at least four of six developers favoring native on the maintenance tasks, and blinded review finding no compensating compiler/kernel or application burden. Report each task separately so an easy extension cannot mask harder maintenance. These are proposed comparison rules, not existing measured gates; change them only before collection and explain the chosen practical margin.
5. **Stop and decide once.** If this passes, the defensible conclusion is “easier to implement/maintain on this declared Three slice and these changes,” with wider R3F parity and long-term costs still unknown. Submit that exact claim and evidence to the prerequisite review. If it fails or is mixed, keep the maintenance claim unproven and identify the specific interface burden to simplify; do not repeatedly tune tasks until they favor native. The user's full review remains held unless the maintenance gate is actually established or the user explicitly changes it.

Fixing the identified cleanup contract and running more native green tests can strengthen Three correctness. They cannot substitute for the comparative proof. The original product requirements remain the scope of the eventual full review; none have been replaced by this narrower prerequisite exercise.
